# Наполнение здания — план реализации этапа 1

## 1. Цель этапа

Первый этап подготавливает формат Blueprint и редактор к системе наполнения из
[«Наполнения здания»](building_furnishing.md), а также исправляет расхождения
текущего редактора с его UX-правилами.

Этап **не добавляет игровую функциональность**. Костёр, станок, кровать,
поддон и прилавок пока остаются визуальными объектами: они не получают
runtime-состояние, не создают задания, не участвуют в логистике и не меняют
поведение AI. Функциональные `fixtures` и интеграция с зонами — следующий этап.

Результат этапа: автор может надёжно создавать, редактировать, сохранять и
мигрировать визуальное наполнение, а формат имеет безопасное место для будущей
функциональности.

## 2. Границы

### Входит в этап

- единый формат визуальных объектов версии 2;
- миграция старых `objects[].properties` в `objects[].appearance`;
- явное, но пока только организационное поле `owner_zone`;
- зарезервированный массив `fixtures: []` без runtime-поведения;
- каталог, поиск, категории и метаданные ассетов;
- корректные привязки, трансформ, замена, инспектор и коллизии preview;
- валидация, миграционные тесты и UI-тесты редактора;
- обновление встроенных Blueprint до нового формата.

### Не входит в этап

- создание или редактирование `FixtureDefinition` в UI;
- `FixtureRuntimeState`, стартовое топливо, включённость или износ;
- отображение runtime-данных в сцене;
- новые AI facts, goals, actuator-команды, резервации и логистика;
- автоматическое создание обязательного оборудования из шаблона зоны;
- меню зон и многофункциональная игровая логика;
- изменение старых игровых костров, складов и рабочих точек.

## 3. Стратегия формата и миграции

### 3.1. Версия

Новый файл сохраняется с `version: 2`. Загрузчик обязан читать версии 1 и 2.
Файлы v1 не переписываются при простом открытии: миграция становится видимой и
выполняется при явном сохранении автора.

### 3.2. Объект v2

```json
{
  "id": "campfire_visual_1",
  "asset_id": "campfire",
  "owner_zone": "",
  "pos": [1.5, 0.0, 1.5],
  "rot": [0, 90, 0],
  "scale": [1, 1, 1],
  "appearance": {
    "light_color": "ffaa44"
  }
}
```

Правила миграции v1 → v2:

1. `properties` копируется в `appearance` без потери JSON-значений.
2. `owner_zone` добавляется пустым.
3. Старый `anchor` не переносится как данные v2: сохраняется итоговый
   трансформ. При загрузке v1 старое смещение учитывается, чтобы объект не
   сдвинулся визуально.
4. `fixtures` добавляется как пустой массив на уровне Blueprint.
5. Неизвестные поля будущих версий сохраняются при read-modify-write, либо
   сохранение блокируется с понятной причиной; поведение выбирается один раз для
   всего Blueprint-формата.

### 3.3. Резерв для следующего этапа

В v2 разрешён только пустой `fixtures: []`. Валидатор отклоняет непустой массив
с сообщением «Функциональные элементы будут доступны на этапе 2». Это позволяет
сразу закрепить форму файла, не создавая полуготовую игровую механику.

`owner_zone` пока не влияет на runtime. Он доступен в инспекторе только как
необязательная организационная метка, выбираемая из существующих `place_zones`.
При удалении зоны редактор предупреждает о предметах с этой меткой и предлагает
снять её; каскадного удаления предметов нет.

## 4. Порядок реализации

### Шаг 1. Доменные записи и сериализация

Изменить `DecorObjectRecord` в целевую запись визуального предмета (переименование
типа допустимо только с совместимым alias или миграцией импортов):

- заменить `properties` на `appearance`;
- добавить `owner_zone_id: StringName`;
- убрать сохранение authoring-`anchor`;
- добавить v1/v2 serializer и мигратор;
- добавить `fixtures` в `BuildingBlueprint` как зарезервированный типизированный
  пустой массив/заглушку;
- добавить ошибки валидации для ссылок на отсутствующую зону и дублирующихся ID.

Критерий готовности: v1 Blueprint загружается без изменения его положения,
сохраняется как v2 и повторно загружается без изменения данных v2.

### Шаг 2. Описание ассетов и каталог

Переименовать концепцию `DecorAssetDef` в `FurnishingAssetDef` или ввести новый
тип с совместимым переходным именем. Добавить метаданные:

- `group`, `category`, `tags`, `available_from_era`;
- `placement_surface`, доступные шаги сетки и default step;
- разрешённые оси вращения;
- `scale_mode` и допустимые масштабы;
- `collision_policy` и отдельный флаг blocking navigation;
- `appearance_controls` вместо общих `controls`;
- задел `supported_capabilities`, который пока не используется редактором
  функций.

Сделать «Оборудование» полноценной группой с категориями: промышленное,
верстаки, инструменты, кухня, склад/логистика, торговля/сервис, коммунальное и
санитарное. Остальные категории привести к таксономии из основного документа.

Критерий готовности: каталог может отфильтровать ассеты по категории, тегу,
эре и поверхности; пустая категория видна, но не ведёт в пустой рабочий режим.

### Шаг 3. Размещение и трансформ

Переписать размещение по политике ассета:

- убрать глобальный «свободный» snap; свободное размещение разрешает только
  ассет;
- заменить сохраняемый `anchor` контекстными командами snap к полу, стене,
  потолку, углу и центру;
- хранить всегда только окончательный `pos`/`rot`/`scale`;
- ограничить вращение и масштаб метаданными ассета;
- добавить корректный ghost с состояниями: допустимо, пересечение, вне границ;
- исправить выбор объектов при перекрытии: сначала ближайший к камере/курсору,
  затем cycle selection;
- гарантировать, что duplicate учитывает разрешённые snap и границы.

Критерий готовности: нельзя получить через инспектор трансформ, который
невозможно получить инструментом размещения.

### Шаг 4. Инспектор и UX редактирования

Реализовать инспектор в секциях:

- «Основное»: ID, asset, `owner_zone`, диагностические badges;
- «Трансформ»: только разрешённые поля и reset/snap-команды;
- «Внешний вид»: controls `appearance`;
- «Связи»: только организационная зона и явная пометка «Функциональность —
  этап 2».

Добавить:

- inline accordion каталога и текстовый поиск;
- недавно использованные ассеты;
- синхронизацию выбранного объекта с каталогом без переключения в placement;
- явную команду «Заменить выбранный объект» с preview потерь свойств;
- redo рядом с undo;
- список объектов с поиском и переходом к объекту;
- понятные disabled-состояния вместо исчезающих команд.

Критерий готовности: все операции над объектом доступны из UI, имеют горячие
клавиши либо discoverable-кнопки и попадают в undo/redo.

### Шаг 5. Коллизии и preview в редакторе

Добавить authoring-preview коллизии независимо от игрового runtime:

- `none`, `box`, `scene`, `footprint`;
- отдельное отображение blocking navigation;
- проверку пересечений с каркасом, проходами и другими blocking-предметами;
- переключатель overlay «Коллизии / проходы».

Эти данные пока не регистрируют реальные навигационные препятствия в игре.

Критерий готовности: автор видит конфликт до сохранения, а визуально маленький
объект не становится препятствием без явно заданной политики.

### Шаг 6. Зоны без функциональности

Добавить минимальную UX-связь с уже существующими `place_zones`:

- выбор зоны-владельца в инспекторе;
- фильтр «показать предметы выбранной зоны»;
- подсветку зоны и предупреждение, если предмет заметно находится вне неё;
- безопасное снятие связи при удалении зоны.

Не добавлять обязательные requirements, anchors-автогенерацию и любые fixtures
UI — это этап 2.

Критерий готовности: автор может организовать интерьер многофункционального
Blueprint по зонам, но ни один предмет от этого не меняет игровую симуляцию.

### Шаг 7. Встроенные данные и документация

- мигрировать встроенные `.gdbuilding.json` в v2;
- перенести текущие authoring-свойства в `appearance`;
- проставить пустой `owner_zone` и `fixtures`;
- добавить минимум по одному ассету в ключевые категории, либо оставить
  категории видимыми как «Скоро появится»;
- обновить README формата и ссылки в модульном редакторе;
- добавить краткое руководство автора: создать → разместить → назначить зону →
  проверить → сохранить.

## 5. Тесты

### Domain

- v1 → v2 миграция каждого поля;
- round-trip v2 без изменения JSON-смысла;
- сохранение конечного трансформа из старого `anchor`;
- уникальность ID и корректность `owner_zone`;
- запрет непустого `fixtures` в этапе 1;
- валидация масштаба, поворота, поверхности и политики коллизии;
- фильтрация каталога по тегам, эре и поверхности.

### Editor

- размещение на каждом допустимом шаге;
- wall/floor/ceiling snap;
- запрет недопустимого трансформа из полей инспектора;
- выбор перекрывающихся предметов;
- duplicate, replace, delete, undo и redo;
- поиск, accordion и синхронизация выбора;
- отображение коллизий и конфликтов;
- назначение и снятие `owner_zone`.

### Регрессия

- все существующие Blueprint загружаются;
- открытие старого Blueprint не меняет файл до явного сохранения;
- старые декор-сцены корректно отображаются;
- основной набор headless-тестов проекта проходит.

## 6. Definition of Done

Этап 1 завершён, когда:

1. Новый Blueprint сохраняется как v2, старый v1 мигрируется предсказуемо.
2. Визуальные свойства и runtime-состояние не смешаны: существует только
   `appearance`; начальных топлива/включённости пока нет.
3. Предмет можно явно отнести к зоне, но это не создаёт игровой функции.
4. Каталог включает полноценное оборудование как визуальные ассеты.
5. Трансформ, замена, выбор и undo/redo согласованы между инструментами и
   инспектором.
6. Редактор показывает коллизии и понятные ошибки размещения.
7. `fixtures: []` зарезервирован, но непустой список невозможно создать,
   сохранить или загрузить как рабочую механику.
8. Domain- и editor-тесты из раздела 5 проходят.

## 7. Переход к этапу 2

Этап 2 начинается после того, как v2 стал единственным форматом записи. Тогда
последовательно добавляются:

1. типизированные `FixtureDefinition` и schema `runtime_defaults`;
2. UI создания fixture и явная связь с визуальным предметом;
3. требования capabilities шаблонов зон;
4. `FixtureRuntimeState` в построенном экземпляре;
5. presentation bindings runtime-состояния;
6. по одному вертикальному игровому срезу — сначала, например, `fire_source`,
   затем `bed`, `storage_*`, `workbench`.

Ни один из этих пунктов не должен попадать в этап 1 частично.
