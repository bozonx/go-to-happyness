# Дизайн-документ: навигация и дороги

## Назначение

Система определяет, по каким клеткам могут передвигаться жители и транспорт, как
выбирается маршрут и как покрытие меняет его стоимость и фактическую скорость.
Дороги являются данными покрытия, а не вторым маршрутизатором: маршрут всегда
строится только через `NavGrid` и `GridRouteService`.

Цели системы:

- жители не проходят через здания, воду и опасные участки;
- более дешёвое покрытие естественно притягивает маршруты;
- изменение препятствий немедленно делает активные маршруты небезопасными, а
  изменение покрытия влияет на выбор следующих маршрутов;
- работа остаётся предсказуемой при большом числе жителей.

## Базовая маршрутизация

Правила, по которым строится маршрут до появления построенных дорог. Тропинки
(desire lines) уже действуют, дороги — ещё нет.

- Клетка без переопределения имеет вес травы `2.0`. `NavGrid` хранит размеры,
  блокировки, общие разреженные переопределения веса и profile-specific
  переопределения.
- Поиск — взвешенный A* по восьми направлениям с допустимой octile-эвристикой,
  умноженной на минимальный вес сетки. Диагональ имеет длину `sqrt(2)` и
  **запрещена**, если хотя бы одна из прилегающих ортогональных клеток
  заблокирована.
- Угол здания не срезается: проверка отрезка смотрит обе клетки при пересечении
  угла.
- Сглаживание пути (weighted string pulling) убирает изгиб, только если прямой
  отрезок не пересекает препятствия **и** стоит не более чем на 8% дороже
  заменяемого участка. Без ограничения по стоимости сглаживание вытаскивало бы
  маршрут с дешёвого покрытия на дорогое.
- Скорость пешехода — `base_speed / cell_weight`; трава с весом `2.0` даёт 50%
  базовой скорости.
- Тропинки живут в отдельной разреженной nav-проекции и применяются только к
  pedestrian-профилю. Визуальный след и nav-проекция — разные данные:
  `TrailFieldService` владеет обоими, `TrailTextureRenderer` в
  `routing/presentation` превращает визуальный слой в текстуру. Application-сервис
  не создаёт rendering resources.

### Две ревизии

`NavGrid` владеет двумя монотонными счётчиками, и разница между ними — контракт,
а не деталь:

| Счётчик | Меняется когда | Обязывает актора |
| --- | --- | --- |
| `revision` | любое реальное изменение размеров, блокировок или весов | нет — новый маршрут может быть дешевле, но старый безопасен |
| `topology_revision` | меняется **проходимость** | да — перепланировать немедленно |

`RouteResult` несёт обе; `RouteResult.is_topologically_stale()` — единственный API
этой проверки. Смена веса покрытия влияет на выбор новых маршрутов и на скорость,
но не отменяет уже построенный безопасный путь.

Недостижимый маршрут повторяется с экспоненциальной задержкой от 2 до 16 секунд;
изменение revision отменяет ожидание и разрешает немедленную попытку.

## Модель стоимости

Для перехода из клетки `A` в соседнюю клетку `B`:

```text
cost(A -> B) = geometric_distance(A, B) * traversal_weight(B, profile)
```

Вес всегда положителен. `1.0` является базовой скоростью пешего движения;
значения меньше `1.0` допустимы для улучшенных дорог. Блокировка не выражается
весом: такая клетка вообще исключается из поиска.

Веса тропинок намеренно близки к базовому весу травы (`2.0`): молодая тропинка
имеет вес `1.7`, полноценная — `1.4`. Это даёт умеренное ускорение (~1.4x для
зрелой тропинки), но не делает его двукратным. Двукратное ускорение (`вес 1.0`)
расширило бы каждый маршрут: A*-эвристика умножается на минимальный вес сетки,
и снижение веса даже нескольких клеток увеличивает эвристическую оценку для
всех маршрутов. Компромисс сохраняет tight heuristic и приемлемую стоимость
поиска по мере роста сети тропинок.

Базовые значения для будущего покрытия:

| Покрытие | Вес | Скорость пешехода |
| --- | ---: | ---: |
| Трава | 2.0 | 50% |
| Песок, кустарник | 3.0–4.0 | 25–33% |
| Болото, густой лес | 8.0 или запрет | 12.5% |
| Полноценная тропинка палаточной эры | 1.4 | 71% |
| Грунтовая дорога | 1.0 | 100% |
| Глинобитная | 0.9 | 111% |
| Деревянная | 0.85 | 118% |
| Каменная | 0.8 | 125% |
| Асфальтовая | 0.7 | 143% |

Игровые коэффициенты из таблицы являются начальными значениями баланса. Скорость
и стоимость должны происходить из одной таблицы покрытия, чтобы маршрут не
предпочитал поверхность, на которой затем движение неожиданно медленнее.

## Контракт маршрутизации

Запрос типизирован (`RouteRequest`): `from`, `destination`, `traveler_profile`,
`allow_destination_cell` и необязательный `profile_override`.

`traveler_profile` обязателен до появления велосипедов, тележек и машин. Он
задаёт доступность покрытия и его вес. Например, тропинка допустима для пешехода,
но не для тележки; грунтовая дорога допустима для тележки, но может иметь штраф
для машины в дождь. Нельзя кодировать эти ограничения только в визуальном типе
дороги или в логике актора.

`RouteResult` содержит `reachable`, `waypoints`, `arrival_position`, обе ревизии
и `unreachable_reason`. Пустой список waypoints **никогда** не означает успешный
маршрут: конструктор `success()` с пустым списком возвращает unreachable.

## Владение данными

`NavGrid` — единственный источник проходимости и итогового веса, который читает
`GridRouteService`. `RoadNetworkService` владеет завершёнными дорожными
покрытиями и применяет их через API `NavGrid`:

```text
RoadNetworkService -> NavGrid.set_road_cell_weights(overrides) -> GridRouteService
```

`NavGrid` хранит независимые слои terrain overrides, pedestrian desire trails и
constructed-road overrides. Приоритет чтения: completed road -> profile trail
-> terrain -> grass. Поэтому демонтаж дороги вновь открывает ещё не заросшую
тропинку, а не уничтожает её данные. Bootstrap публикует только world facts;
`NavigationObstaclePublisher` превращает terrain и building footprints в
blocked cells.

Routing вынесен в отдельную feature `routing` (`game/features/routing/`), что
соответствует `docs/architecture.md`: выбор маршрута не зависит от `Citizen`, UI
или bootstrap-контроллера.

## Дороги

| Тип | Пешеход | Кто ещё допускается |
| --- | ---: | --- |
| Тропинка | 100% | никто: только пешеход |
| Грунтовая | 100% | индивидуальная мобильность |
| Глинобитная | 110% | индивидуальная мобильность |
| Деревянная | 120% | индивидуальная мобильность |
| Каменная | 130% | индивидуальная мобильность |
| Асфальтовая | 140% | индивидуальная мобильность |

**Когда покрытие становится доступно, решает игра, а не движок.** Запись покрытия
несёт условие разблокировки (для поселения — технология,
[eras_overview.md](../settlement/eras_overview.md) §4), а не номер эры: routing не
обязан знать перечисление эр чужой игры. В коде это условие пока хранится числом
эры (`CoverageCatalog.min_era`) — легаси моно-игры, подлежащее замене на ссылку на
условие разблокировки.

Более поздние покрытия — выделенные полосы, рельсы, эко-плитка — отдельной записи
не имеют: они появляются вместе со своим потребителем
([../ideas.md](../ideas.md) §1).

При ручной постройке клетка остаётся исходным покрытием до завершения работ.
После завершения `RoadNetworkService` меняет override веса, визуал и revision
сетки одной транзакцией. Улучшение дороги использует тот же процесс и не меняет
проходимость мгновенно.

### Каталог покрытий вместо веток кода

Таблица выше — **содержимое каталога, а не структура кода**. Сейчас `RoadType`
реализован статическим `match` по весам, эрам и профилям; это временная форма.
Покрытие обязано описываться записью данных, потому что пак без кода пользуется
механикой хоста декларативно (`content_packaging.md`), и инопланетный настил не
должен требовать ни новой системы, ни правки GDScript.

| Поле записи | Смысл |
| --- | --- |
| `id` | стабильный строковый ID (`core:dirt`, `pack:a.b/alien_deck`) |
| `weight` | вес перехода, публикуемый в `NavGrid` |
| `profiles[]` / `surface_tags[]` | какие `TravelerProfile` допускаются |
| `unlock` | условие разблокировки постройки игроком: ссылка на условие игры (для поселения — технология) |
| `flags` | `organic`, `no_wear`, `no_regrowth`, … |
| `texture`, `variants[]` | внешний вид |

Ограничение типа покрытия проверяется по одному реестру профилей, а не по
расходящимся строкам `cart`, `bicycle`, `motor`; старые идентификаторы остаются
явными compatibility aliases для сейвов (см. «Дороги и транспорт»).

**Тропинка — такая же запись с флагом `organic`.** Она по-прежнему возникает от
трафика и живёт в своей nav-проекции, но перестаёт быть исключением в каталоге:
редактор карт может нанести стартовую тропу с начальной `path_strength`, и
заброшенная деревня авторится, а не ждёт, пока жители её протопчут.

Хранение авторского слоя покрытий (`surface.bin`: `coverage_index` + детальный
байт `variant | wear | snow`), инструменты укладки и правило «карта сеет
`RoadNetworkService` при загрузке, дальше владелец записи — сервис» описаны в
[map_editor.md](map_editor.md) §5.2.1–5.2.3.

## Desire lines и трафик

В начале палаточной эры поляна покрыта травой. Она проходима, но имеет вес `2.0`,
поэтому жители двигаются по ней вдвое медленнее базовой скорости. Тропинки не
строятся игроком: они возникают там, где жители действительно ходят. Это делает
первые маршруты медленными и постепенно формирует понятную, живую сеть между
костром, палатками, складом, рабочими местами и часто посещаемыми ресурсами.

Визуальный след тропинки непрерывен: он ставится вдоль фактического отрезка
движения жителя и не обязан проходить через центры клеток. Навигационное влияние
следа дискретно, потому что текущий маршрутизатор работает через `NavGrid`.
Поэтому сервис тропинок агрегирует пройденные отрезки в затронутые nav-клетки и
начисляет трафик только при входе жителя в новую nav-клетку, не на каждом кадре и
не на каждом физическом шаге. Это исключает зависимость от FPS и скорости
симуляции.

```text
record_walker_position(walker_id, position, road_walking)
  -> если горизонтальное смещение >= SAMPLE_DISTANCE:
    -> stamp_segment(from, to, stamp_strength)      # визуальный след
    -> для каждой новой nav-клетки на отрезке:
      -> traffic[cell] += traffic_strength * (2.0 if road_walking else 1.0)
      -> обновить навигационное состояние тропинки для этой клетки
```

`movement_mode` не является отдельным маршрутизатором и не меняет доступность
клеток. Он влияет только на то, насколько заметно житель протаптывает маршрут.
Обычное движение использует множитель `1.0`; режим «ходить как по дороге» —
повышенный множитель. Настройка относится к приказу поселения, а не к отдельному
жителю, поэтому все жители используют одинаковое правило, пока приказ активен.
Это постоянная глобальная политика костра, а не дневный приказ отдельным
жителям: она сохраняется между днями, пока игрок не выключит ее вручную.

Тепловая карта визуала хранится отдельно от nav-состояния и может быть плотной
текстурой или разреженным полем. Nav-состояние разреженное: `traffic[cell]`
хранится только для клеток, где был заметный поток. Раз в игровые сутки значения
умножаются на `1 - decay_rate`; значения ниже epsilon удаляются. Для
автопревращения в тропинку и деградации нужны разные пороги и задержка в
несколько дней, иначе покрытие будет мигать около границы:

- `path_create_threshold` переводит траву в молодую тропинку;
- `path_mature_threshold` переводит молодую тропинку в полноценную;
- `path_degrade_threshold < path_create_threshold` начинает деградацию;
- деградация завершается только после `N` подряд игровых дней ниже порога.

### Тропинки палаточной эры

Пока не разблокировано ни одно строящееся покрытие, игрок не может размещать
чертежи дорог, улучшать тропинки вручную или расходовать на них ресурсы. Единственное дорожное покрытие эпохи — тропинка,
созданная трафиком жителей. Визуально она является органической desire-line
полосой по фактическому движению жителей, а не клеточной плиткой. Для навигации
она проецируется в nav-клетки, через которые проходит накопленный след. Это
покрытие доступно только пешеходному профилю и не считается дорогой для
транспорта.

Состояния клетки:

| Состояние | Условие | Вес | Визуал |
| --- | --- | ---: | --- |
| Трава | Трафик ниже порога создания | 2.0 | Обычная трава |
| Молодая тропинка | Достигнут `path_create_threshold` | 1.7 | Узкая полупрозрачная бежевая полоса поверх травы |
| Полноценная тропинка | Достигнут `path_mature_threshold` | 1.4 | Непрозрачная бежевая полоса по протоптанной линии |
| Зарастающая тропинка | После задержки ниже порога деградации | 1.7 -> 2.0 | Бежевый слой постепенно бледнеет и сужается |

Переход между состояниями плавный визуально, но навигационный вес меняется только
на указанных порогах. Визуальная ширина и непрозрачность зависят от нормированного
`path_strength` внутри клетки: след сначала проявляется бледной тонкой линией,
затем становится шире и заметнее. Максимальная ширина ограничена шириной
пешеходной тропы; она не превращается в клеточную дорогу и не расширяется от
интенсивного потока.

Пока трафик поддерживает `path_strength`, тропинка сохраняется. Если жители долго
не ходят по ней, суточное затухание снижает силу следа. После `N` подряд игровых
дней ниже `path_degrade_threshold` клетка становится зарастающей, а затем
возвращается к траве и удаляет override веса из `NavGrid`. Любой новый проход до
окончательного исчезновения повышает силу следа и отменяет деградацию.

### Приказ «Ходить как по дорогам»

У костра есть кнопка приказов, открывающая модальное окно приказов
поселения. В палаточной эре в нём доступен переключатель **«Ходить как по
дорогам»**. Он не рисует путь и не создаёт покрытие мгновенно: приказ велит
жителям при обычных переходах двигаться более собранно и сильнее протаптывать
выбранные маршруты.

- Включённый приказ устанавливает `movement_mode = road_walking` для новых и
  продолжающихся маршрутов жителей; начисление трафика использует повышенный
  `movement_mode_traffic_multiplier`.
- Приказ не отменяет критические потребности, прямое управление, запреты
  проходимости и другие правила `OrderBoard`; он является глобальной политикой
  движения, применяемой актуатором при исполнении маршрута.
- Переключение применяется сразу к последующим переходам клеток. Уже созданные
  тропинки не получают силу задним числом.
- Приказ сохраняется между днями и выключается только вручную через меню
  приказов костра.
- В модальном окне показываются активное состояние приказа и краткий эффект:
  жители быстрее формируют тропы, но не получают дополнительной скорости на
  траве до появления самой тропинки.

После появления тропинки маршрут уже сам предпочитает её: A* минимизирует
стоимость переходов, а вес тропинки ниже веса травы. Поэтому жители выбирают
немного более длинный, но более лёгкий маршрут по существующим тропам, продолжают
его протаптывать и стабилизируют полезные направления. Если обход по тропинке
дороже прямого пути по траве, выбирается прямой путь; система не должна
искусственно заставлять жителя делать неразумный крюк.

Автоулучшение грунтовой дороги создаёт обычный строительный заказ с ограничением
дневного бюджета, приоритетом ниже жизненно важных работ и явной проверкой эпохи,
исследований и ресурсов. Каменные и более качественные дороги сами не деградируют.

## Производительность и надёжность

- Минимальный вес кэшируется в `NavGrid` и пересчитывается только при изменении
  overrides.
- Для A* используется бинарная очередь; поиск не должен делать линейный обход
  очереди или всей сетки на каждом соседнем переходе.
- Очередь route requests должна иметь бюджет на кадр, когда население вырастет.
  Одинаковые запросы к той же цели можно кэшировать по revision.
- При изменении revision активные и отрицательные маршруты устаревают сразу.
- Сглаживание допускается только по проверенному `segment_cost`; полученные
  waypoints не являются достаточной проверкой безопасности сами по себе.

## Тесты

Минимальный набор автоматических проверок:

- достижимый и недостижимый маршрут;
- запрет диагонального срезания угла;
- выбор более длинного, но дешёвого коридора;
- сохранение корректных сегментов после сглаживания;
- изменение blocked cells увеличивает `topology_revision` и делает активный
  `RouteResult` небезопасным; изменение веса увеличивает только `revision` и
  применяется при следующем выборе маршрута;
- повторная установка идентичных данных не меняет revision;
- производительный маршрут на максимальном размере игрового поля;
- недостижимый маршрут не выполняется повторно до изменения revision или таймера.
- трафик начисляется ровно один раз при входе в клетку и не зависит от FPS;
- обычные проходы создают молодую и затем полноценную тропинку только после
  соответствующих порогов, а приказ `road_walking` ускоряет этот набор;
- тропинка имеет ширину одной клетки, снижает маршрутную стоимость и не доступна
  непешеходному профилю;
- неиспользуемая тропинка проходит задержку деградации, удаляет override веса и
  возвращается к траве; новый проход до удаления отменяет деградацию.
- покрытие, добавленное только записью каталога (без правки кода), получает свой
  вес, свои допустимые профили и свой гейт эры; неизвестный `id` fail-closed.
- снос покрытия над недозаросшей тропинкой возвращает вес тропинки, а не травы.

## Перспективы развития и границы архитектуры

Подсистема разделяется прежде всего по **топологии пространства**, а не по
названию транспорта. У неё две независимые оси: граф, где возможен путь, и
физические возможности путешественника. Исполнение уже найденного пути — это
потребитель маршрутизации, а не третья ось поиска.

### Графы пространства

| Граф | Когда нужен | Текущее состояние |
| --- | --- | --- |
| `TerrainGrid` | Открытая местность, покрытие, тропинки и off-road движение | Реализован как `NavGrid` + `GridRouteSolver`. |
| `IndoorGraph` | Комнаты, двери, этажи, лестницы, шлюзы и бункеры | Добавляется, когда появляется первая многоуровневая или дверная топология. Не дублирует terrain grid. |
| `RoadLaneGraph` | Полосы, направления, перекрёстки, обгоны, остановки и правила трафика | Не создаётся для простого дорожного покрытия. До этих механик дорога остаётся весом в `TerrainGrid`. |
| `AirGrid` | Реальное трёхмерное воздушное пространство и воздушные препятствия | Добавляется вместе с летающими агентами. |

Переход между разными графами происходит только через типизированный portal
(например, дверь `Indoor <-> Terrain`, въезд `Terrain <-> RoadLane`). Composite
solver не имеет права «угадывать» переход по близким координатам: portal должен
явно содержать обе точки входа, разрешённые профили и состояние проходимости.
До появления portal-модели composite solver не создаётся: production-путь
использует только `GridRouteSolver`. Первый composite implementation добавляется
одновременно с типизированными portal records и вторым реальным графом.

### Профили мобильности

`TravelerProfile` — value-style контракт одного запроса маршрута; после
создания экземпляр рассматривается как неизменяемый. У профиля
есть стабильный конкретный `profile_id` для сохранений и контента, а также
крупная `mobility_category` только для группировки. Новому транспорту не нужен
новый solver, если его геометрия совпадает с существующим графом.

Категорий ровно три, и каждая существует потому, что у неё есть или вот-вот будет
реальный потребитель:

| Категория | Примеры | Что отличает |
| --- | --- | --- |
| `pedestrian` | житель вне дорог | ходит везде, где проходимо; покрытие только ускоряет |
| `pedestrian_road` | житель под приказом «ходить как по дорогам» | то же движение, но сильнее тяготеет к покрытию и заметнее его протаптывает |
| `personal_mobility` | велосипед и прочая индивидуальная мобильность | движется только по допустимым покрытиям, вне их — теряет смысл |

Конкретный профиль задаёт разрешённые graph layers, off-road доступ и допустимые
дорожные поверхности. Текущий плоский `NavGrid` не заявляет, что проверяет факты,
которых world ещё не публикует.

Грузовой, тяжёлый внедорожный и воздушный транспорт, а также роботы — направления,
а не категории: они вынесены в [../ideas.md](../ideas.md) §6.4 и получают запись в
реестре профилей только вместе со своим потребителем. Плодить категории заранее
нельзя: каждая из них — обещание проверок, которых мир не делает.

Строковые идентификаторы допустимы только на внешней границе совместимости.
Перед поиском `RouteRequest.get_profile()` обязан дать зарегистрированный
`TravelerProfile`; неизвестный профиль fail-closed с `PROFILE_UNSUPPORTED`, а
не начинает двигаться как пешеход.

### Дороги и транспорт

Покрытие и дорожный граф — разные понятия. `RoadNetworkService` по-прежнему
владеет построенным покрытием и публикует его веса в `NavGrid`. Велосипед —
это профиль на terrain grid, а не отдельный роутер. Только появление полос и
правил движения оправдывает `RoadLaneGraph`, и до появления такого транспорта
он не создаётся.

Ограничения типа покрытия проверяются по одному реестру профилей, а не по
расходящимся строкам `cart`, `bicycle`, `motor`: дорожное определение объявляет
требуемые capability/surface tags, а не имя транспорта.

`RoadNetworkService` сейчас является завершённым application-владельцем
покрытия и save/load state, но команда строительства дорог игроком ещё не
реализована. Она должна появиться единым vertical slice: typed road order,
строительство, completion command в `RoadNetworkService` и демонтаж. До этого
bootstrap не имитирует завершение дороги и не создаёт второго write-owner.

Укладка игроком **переиспользует растеризатор редактора карт**
(`coverage_rasterizer.gd`, [map_editor.md](map_editor.md) §5.2.1): игрок тянет
мазок или сплайн-штрих, клетки получают чертёж покрытия, дальше это обычный
строительный заказ, а completion пишет тот же слой, который в редакторе пишет
автор. Двух реализаций укладки не существует, и перекрёстки в обоих случаях
решаются данными — клетка принадлежит ровно одному покрытию.

### Маршрутные планы, патрули и формации

Маршрутная линия, расписание и патруль не являются graph layer и не получают
свой поиск пути. Это `RoutePlan`: стабильный ID, упорядоченные остановки,
режим цикла, время ожидания и профиль транспорта. Планировщик запрашивает
обычный `RouteRequest` для каждого участка «остановка -> остановка», кэширует
его по revision и перепланирует участок при изменении topology revision.

Формация и колонна также исполняют маршрут, а не строят свой. Лидер получает
маршрут через `NavigationFacade`; ведомые получают безопасные локальные цели
из citizen-side formation controller. Расчёт смещений может быть чистым
application-кодом, но движение, физика и avoidance остаются в
`citizens/presentation`. `routing` не владеет `Citizen` или `Node3D`.

### Точки расширения в GDScript

- `NavigationFacade.find_route_request(RouteRequest)` — единственный публичный
  порт для новых потребителей. Он может быть сконфигурирован текущим
  `GridRouteService` или будущим `RouteSolver` без изменения callers.
- `RouteSolver` — минимальный контракт solver’а. `GridRouteSolver` обслуживает
  только terrain layer; future indoor, lane и air solver’ы реализуют тот же
  контракт.
- `NavigationPortal`, `RouteSegment` и настоящий composite поиск добавляются
  одной вертикальной задачей вместе с первым вторым графом; не раньше.
- `RoutePlan` принадлежит feature-владельцу расписания (например, logistics
  для маршрута доставки, decision для патруля), а не `routing`. Routing владеет только
  запросом и результатом каждого участка.

### Лаборатория и тесты

Когда ставить сцену для отладки, а когда хватает тестов, подчиняется тем же
правилам, что и террейн и вода: тесты доказывают детерминированные инварианты,
лаборатория нужна только для визуальных свойств, которые число не утверждает.

Тесты покрывают:

- приоритет слоёв веса (`road -> trail -> terrain -> grass`);
- оба счётчика — `revision` vs `topology_revision` — и контракт
  `RouteResult.is_topologically_stale()`;
- запрет срезания угла здания и проверку отрезка по обеим клеткам;
- ограничение стоимости сглаживания (≤ 8 % удорожания) и безопасность
  сглаженных сегментов;
- fail-closed на неизвестном `traveler_profile` / `profile_id`;
- правила тропинок, пороги, задержку деградации и отмену новым проходом;
- запись каталога покрытия без правки кода получает свой вес, свои профили и
  своё условие разблокировки.

Этого достаточно для всего, что есть сегодня: единственный реальный граф —
террейн (`GridRouteSolver`), а реально различаются пока только пешие профили.

Визуальная ось, которую тесты не доказывают — **проходимость**, — уже живёт в
`tools/terrain_lab/`: боевой `NavGrid`, оверлей по клавише `M` и переключатель
профиля по `T`. Дублировать её в отдельной «навигационной лаборатории» нельзя —
это форк `nav_terrain_overlay` и `--capture`, а один инструмент на concern
должен шариться между хостами (террейн-лаб, редактор карт, редактор зданий).

**Поэтому отдельной лаборатории роутинга не существует, пока не появляется
второй граф пространства.** Новые возможности расширяют terrain_lab:

- новый профиль — добавляется в переключатель `T` и capture-набор;
- дороги — capture-сценарий «коридор дешевле травы»;
- тропинки — визуальный след в существующем окне.

Отдельная лаборатория получает право на существование только вместе с первым
`IndoorGraph` + типизированными portal records + composite solver — это
3D-пространственная топология (комнаты, двери, порталы), которая визуальна
способом, которым террейн не является. Она строится как единый vertical slice
с портальной моделью и Composite-реализацией, по тем же правилам, что и сами
графы выше, и сразу с MCP-совместимым `--capture`. До портальной модели
production-путь идёт только через `GridRouteSolver`, и отдельной сцены нет.

«Лаборатория по транспорту» или «по животным» — неверный фрейм: подсистема
делится по топологии пространства, а не по виду путешественника. Пешеход и
велосипед ходят по одному графу с разными `TravelerProfile`. Такой лаборатории
не появляется.
