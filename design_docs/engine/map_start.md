• Да — сейчас понятие «стартовые данные карты» смешивает несколько разных сущностей. Для игры-хоста, где пользовательские паки
  могут создавать поселение, приключение, арену или другую игру, я бы разделил их явно.

  Главная модель:

  Карта
  ├── Неизменяемая география мира
  ├── Варианты старта на этой карте
  ├── Начальное состояние объектов мира
  ├── Ограничения сценария
  └── Сценарные переменные времени выполнения

  Game definition
  ├── Состав модулей
  ├── Правила игры
  ├── Дефолтные стартовые параметры
  └── Параметры, доступные игроку перед запуском

  Сессия
  └── Результат объединения:
      game defaults → вариант старта карты → выбор игрока → сценарные изменения

  ## Что считать константами, а что переменными

  Я бы вообще не использовал в UI слова «константы» и «переменные» для всех стартовых данных. Они описывают не назначение
  данных, а возможность изменения во время сессии.

  Нужны четыре категории.

  ### 1. Свойства мира

  Это авторские характеристики карты:

  - размер и шаг сетки;
  - граница: океан/пустота и уровень океана;
  - широта;
  - исходный день года;
  - исходное время;
  - стартовая погода;
  - визуальный стиль;
  - физическое окружение, если карта действительно необычная;
  - обязательный контент и зависимости.

  Они сохраняются в карте. Некоторые из них после старта могут измениться: время идёт, погода меняется. Но это не делает их
  «сценарными переменными» — карта просто задаёт начальное значение соответствующей системы.

  ### 2. Параметры запуска

  Это значения, которые разрешаются один раз перед созданием сессии:

  - численность группы;
  - сложность;
  - эра;
  - стартовый капитал;
  - выбранный старт;
  - вариант загрузки/снаряжения;
  - seed;
  - возможно, сезон или время суток, если автор разрешил игроку их менять.

  После запуска это уже не параметры, а состояние соответствующих игровых модулей.

  Текущий механизм StartParameterDef движется в правильном направлении, но пока поддерживает только int, bool, string, enum.
  Для полноценного редактора ему не хватает:

  - float;
  - content reference — выбор ресурса, архетипа, предмета;
  - списка и словаря;
  - диапазона;
  - локализованного описания и подсказки;
  - категории;
  - признака видимости;
  - признака «игрок может менять»;
  - условий доступности;
  - единиц измерения;
  - шага ввода.

  Сейчас это видно в game/features/runtime/domain/start_parameter_def.gd:1.

  ### 3. Начальное состояние мира

  Это уже не просто числа:

  - лежащий на земле рюкзак;
  - склад с содержимым;
  - размещённая техника;
  - стартовые здания;
  - NPC с конкретными профилями;
  - предметы у персонажей;
  - разрушенный мост;
  - открытая дверь;
  - горящий дом.

  Такое состояние лучше хранить через размещённые сущности и их компоненты, а не раздувать start.module_settings.

  ### 4. Сценарное состояние

  Это изменяемое во время игры состояние сценария:

  - открылся ли проход;
  - активирована ли волна;
  - сколько целей уничтожено;
  - спасён ли персонаж;
  - какой этап задания активен;
  - выбрал ли игрок сторону.

  Текущие flags подходят как низкоуровневый механизм. В UI их лучше называть «Переменные сценария», а не «Стартовые данные».
  Желательно поддержать хотя бы типы bool, int, float, StringName, а не превращать всё в неявные Variant-значения.

  ## Старт — это не одна точка, а стартовый вариант

  Ваше предложение о нескольких точках правильное, но одного списка spawn-точек недостаточно. Лучше ввести сущность уровня выше
  — StartOption или EntryPoint.

  Например:

  {
    "id": "north_camp",
    "name": "Северный лагерь",
    "default": true,
    "enabled_for": ["core:settlement"],
    "spawn_group": "north_party",
    "camera_anchor": "north_camera",
    "loadout": "poor_supplies",
    "parameter_overrides": {
      "gth.settlement": {
        "starting_money": 200
      }
    },
    "tags": ["easy", "near_forest"]
  }

  Другой вариант старта на той же карте может вести к южному порту, иметь другой обзор, окружение и стартовый набор.

  Это даёт:

  - выбор места в свободной игре;
  - фиксированный старт в сценарии;
  - разные старты игроков в мультиплеере;
  - разные стартовые условия на одной географии;
  - переиспользование карты разными game definitions;
  - тестирование каждого старта отдельно.

  ### Как выбирать старт по умолчанию

  Не стоит использовать порядок массива. Перестановка элементов редактором неожиданно изменит поведение карты.

  Лучше:

  - default_start_id на уровне карты; либо
  - default: true у одного старта с проверкой уникальности.

  Я предпочитаю default_start_id: один явный источник истины. Если он отсутствует:

  1. при единственном старте выбрать его;
  2. при нескольких потребовать выбор;
  3. для тестового запуска можно временно выбрать первый, но показать предупреждение.

  ## Что делать с точками героя и компаньонов

  Сейчас карта ожидает отдельную core:hero_start и по одной core:companion_start на каждого жителя. Валидатор напрямую
  связывает количество населения с количеством точек. Это видно [map_validator.gd]home/code-happ/features/world/application/
  map_validator.gd:85).

  Для переменной численности группы это слишком жёстко. область
  ├── orientation
  ├── leader slot
  ├── explicit slots[0..N]
  ├── fallback formation
  ├── allowed actor tags
  └── capacity


  Алгоритм:

  1. Лидер занимает именованный `leader`-слот.
  2. Компаньоны занимают явные слоты по приоритету.
  3. Если персонажей больше — система достраивает формацию внутри spawn-area.
  4. Каждая позиция проверяется по навигации, воде, уклону, коллизиям и профилю перемещения.
  5. Если вместимости недостаточно — запуск блокируется с понятной ошибкой.

  Явные точки всё равно полезны для постановочных сценариев, но не должны быть единственным способом разместить группу.

  Нужны разные семантики:

  - `party_spawn` — группа игрока;
  - `actor_spawn` — конкретный авторский NPC;
  - `reinforcement_spawn` — место будущего сценарного появления;
  - `player_spawn` — слот игрока/команды;
  - `camera_start` — начальный вид;
  - `respawn` — отдельная механика, не равная начальному старту.

  При этом закрытый список ролей можно сохранить (`spawn` остаётся геометрической ролью), а конкретное значение выражать через
  `function` и данные компонента.

  ## Ресурсы и снаряжение

  Здесь нужен не один способ, а три — для разных намерений.

  ### Дефолт игры

  «В обычном Settlement игрок начинает с 500 монетами» — это дефолт game definition или модуля.

  Это уже примерно так работает в [settlement.gdgame.json](/home/ivank/_personal/codeWorkspace/go-to-happyness/game/content/
  core/games/settlement.gdgame.json:1).

  ### Ограничение или вариант карты

  «На этой суровой карте стартовый бюджет ограничен 200 монетами» — override стартового варианта карты.

  Но карта не должна знать общий словарь всех возможных ресурсов движка. Override принадлежит модулю:

  ```json
  "module_settings": {
    "gth.settlement": {
      "starting_money": 200
    }
  }

  ### Физические предметы в мире

  «У северного старта стоит телега с едой и инструментами» — сущность карты с inventory/container-компонентом.

  Это особенно важно для приключений:

  - предмет можно не заметить;
  - его можно украсть;
  - рюкзак может лежать в другом месте;
  - разные персонажи могут иметь разные предметы;
  - контейнер существует физически и сохраняется.

  Таким образом:

  - деньги, репутация, wellbeing — параметры модуля;
  - физические ресурсы и оборудование — inventories сущностей;
  - стартовый личный loadout — профиль состава группы либо inventory конкретного actor;
  - набор, зависящий от выбранного старта, — ссылка loadout_id из StartOption.

  Сейчас в коде уже намечено решение через backpack entity, но документация одновременно говорит, что вся стартовая экономика
  задаётся game definition. Это стоит привести к одному ясному правилу.

  ## Компаньоны

  Нужно разделить количество, состав и размещение.

  - party_size — параметр запуска.
  - party_roster — конкретный состав.
  - party_template — правила генерации состава.
  - spawn_group — только размещение.
  - loadout — предметы и оснащение.

  Точка спавна не должна решать, кто является компаньоном и что у него в карманах. Иначе геометрия карты начинает владеть
  правилами граждан, классов и инвентаря.

  Для карты возможны три режима состава:

  - generated — модуль создаёт N персонажей;
  - fixed — сценарий задаёт конкретных персонажей;
  - player_selected — игрок собирает группу перед запуском.

  В StartOption достаточно ссылки на roster/template, но интерпретирует её соответствующий модуль.

  ## Гравитация и высота прыжка

  Их не стоит ставить рядом как параметры карты: это данные разных уровней.

  ### Гравитация

  Гравитация — свойство мира или физического окружения. Она уже присутствует в BiomeDefinition, что концептуально спорно: биом
  «летний лес» не должен определять физические законы.

  Лучше ввести world physics profile:

  "environment": {
    "physics_profile": "core:earth",
    "gravity": [0, -9.8, 0]
  }

  Но обычный редактор должен показывать только профиль:

  - Земля;
  - Луна;
  - Марс;
  - Невесомость;
  - пользовательский профиль.

  Ручной вектор гравитации — только в расширенном режиме. И обязательно требуется валидация модулей: settlement-навигация,
  вода, частицы и AI могут не поддерживать боковую или нулевую гравитацию.

  Кроме того, нельзя поменять только CharacterBody3D. Гравитацию должны согласованно получать:

  - персонажи;
  - физические тела;
  - снаряды;
  - прыжки;
  - эффекты;
  - расчёт падения;
  - возможно, навигационные профили.

  ### Высота прыжка

  Это свойство не карты, а mobility/actor profile:

  - герой может прыгать на 1,2 м;
  - тяжёлый NPC — на 0,4 м;
  - робот — не прыгает;
  - существо — на 2,5 м.

  Карта может ограничить правило игры вроде «прыжок отключён», но базовая высота должна принадлежать архетипу персонажа или
  модулю управления.

  И лучше хранить именно желаемую высоту и время достижения вершины, а начальную скорость вычислять относительно гравитации:

  jump_velocity = sqrt(2 × |gravity| × jump_height)

  Иначе смена земной гравитации на лунную полностью меняет высоту прыжка.

  Для автора карты важнее не поле «высота прыжка», а валидатор достижимости: способен ли выбранный traveller profile пройти от
  старта к обязательным целям.

  ## Каким должен быть UI

  Текущий единый диалог старта станет тесным. Я бы сделал отдельное рабочее пространство «Старт», а «Сценарий» оставил для
  runtime-правил.

  ### Раздел «Мир»

  - game definition;
  - стиль;
  - календарь и время;
  - погода;
  - physics profile;
  - progression policy;
  - seed policy: случайный, фиксированный, выбираемый игроком.

  ### Раздел «Варианты старта»

  Список слева, карточка справа:

  - ID и локализованное название;
  - доступные game definitions;
  - spawn group;
  - camera anchor;
  - loadout/roster;
  - overrides модулей;
  - доступен ли выбор игроку;
  - условия доступности;
  - кнопка «Сделать стартом по умолчанию»;
  - «Проверить» и «Тестовый запуск отсюда».

  ### Раздел «Параметры игры»

  Генерируется из GameModule.start_parameters(), а не содержит захардкоженные элементы Settlement:

  - значение по умолчанию;
  - override карты;
  - разрешено ли игроку менять;
  - допустимый диапазон;
  - итоговое вычисленное значение.

  Хороший UX показывает происхождение:

  Стартовое население: 6
  Источник: вариант старта «Северный лагерь»
  Дефолт игры: 4
  Игрок может менять: 1…12

  ### Раздел «Начальные сущности»

  Не дублирует редактор наполнения, а показывает связанные объекты:

  - состав группы;
  - контейнеры;
  - транспорт;
  - стартовые здания;
  - недостающие ссылки на контент.

  ### Раздел «Переменные сценария»

  - тип;
  - начальное значение;
  - описание;
  - кто читает/пишет;
  - ссылки на правила;
  - предупреждение о неиспользуемых переменных.

  ## Что ещё важно учесть

  Для пользовательских карт и паков особенно нужны:

  - Локализованные имена и описания стартов.
  - Стабильные ID — никогда не связывать данные по позиции в массиве.
  - Версии схем параметров модулей.
  - Поведение при отсутствии требуемого пака.
  - Обнаружение неизвестных module overrides без уничтожения данных.
  - Возможность одной карты поддерживать несколько game definitions.
