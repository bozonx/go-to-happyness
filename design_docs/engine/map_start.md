• Да — сейчас понятие «стартовые данные карты» смешивает несколько разных сущностей. Для игры-хоста, где пользовательские паки
  могут создавать поселение, приключение, арену или другую игру, я бы разделил их явно.

  Главная модель:

  Карта
  ├── Неизменяемая география мира
  ├── Варианты старта на этой карте
  ├── Начальное состояние объектов мира
  ├── Ограничения сценария
  └── Сценарные переменные времени выполнения

  Game definition
  ├── Состав модулей
  ├── Правила игры
  ├── Дефолтные стартовые параметры
  └── Параметры, доступные игроку перед запуском

  Сессия
  └── Результат объединения:
      game defaults → вариант старта карты → выбор игрока → сценарные изменения

  ## Что считать константами, а что переменными

  Я бы вообще не использовал в UI слова «константы» и «переменные» для всех стартовых данных. Они описывают не назначение
  данных, а возможность изменения во время сессии.

  Нужны четыре категории.

  ### 1. Свойства мира

  Это авторские характеристики карты:

  - размер и шаг сетки;
  - граница: океан/пустота и уровень океана;
  - широта;
  - исходный день года;
  - исходное время;
  - стартовая погода;
  - визуальный стиль;
  - физическое окружение, если карта действительно необычная;
  - обязательный контент и зависимости.

  Они сохраняются в карте. Некоторые из них после старта могут измениться: время идёт, погода меняется. Но это не делает их
  «сценарными переменными» — карта просто задаёт начальное значение соответствующей системы.

  ### 2. Параметры запуска

  Это значения, которые разрешаются один раз перед созданием сессии:

  - численность группы;
  - сложность;
  - эра;
  - стартовый капитал;
  - выбранный старт;
  - вариант загрузки/снаряжения;
  - seed;
  - возможно, сезон или время суток, если автор разрешил игроку их менять.

  После запуска это уже не параметры, а состояние соответствующих игровых модулей.

  Текущий механизм StartParameterDef движется в правильном направлении, но пока поддерживает только int, bool, string, enum.
  Для полноценного редактора ему не хватает:

  - float;
  - content reference — выбор ресурса, архетипа, предмета;
  - списка и словаря;
  - диапазона;
  - локализованного описания и подсказки;
  - категории;
  - признака видимости;
  - признака «игрок может менять»;
  - условий доступности;
  - единиц измерения;
  - шага ввода.

  Сейчас это видно в game/features/runtime/domain/start_parameter_def.gd:1.

  ### 3. Начальное состояние мира

  Это уже не просто числа:

  - лежащий на земле рюкзак;
  - склад с содержимым;
  - размещённая техника;
  - стартовые здания;
  - NPC с конкретными профилями;
  - предметы у персонажей;
  - разрушенный мост;
  - открытая дверь;
  - горящий дом.

  Такое состояние лучше хранить через размещённые сущности и их компоненты, а не раздувать start.module_settings.

  ### 4. Сценарное состояние

  Это изменяемое во время игры состояние сценария:

  - открылся ли проход;
  - активирована ли волна;
  - сколько целей уничтожено;
  - спасён ли персонаж;
  - какой этап задания активен;
  - выбрал ли игрок сторону.

  Текущие flags подходят как низкоуровневый механизм. В UI их лучше называть «Переменные сценария», а не «Стартовые данные».
  Желательно поддержать хотя бы типы bool, int, float, StringName, а не превращать всё в неявные Variant-значения.

  ## Старт — это не одна точка, а стартовый вариант

  Ваше предложение о нескольких точках правильное, но одного списка spawn-точек недостаточно. Лучше ввести сущность уровня выше
  — StartOption или EntryPoint.

  Например:

  {
    "id": "north_camp",
    "name": "Северный лагерь",
    "default": true,
    "enabled_for": ["core:settlement"],
    "spawn_group": "north_party",
    "camera_anchor": "north_camera",
    "loadout": "poor_supplies",
    "parameter_overrides": {
      "gth.settlement": {
        "starting_money": 200
      }
    },
    "tags": ["easy", "near_forest"]
  }

  Другой вариант старта на той же карте может вести к южному порту, иметь другой обзор, окружение и стартовый набор.

  Это даёт:

  - выбор места в свободной игре;
  - фиксированный старт в сценарии;
  - разные старты игроков в мультиплеере;
  - разные стартовые условия на одной географии;
  - переиспользование карты разными game definitions;
  - тестирование каждого старта отдельно.

  ### Как выбирать старт по умолчанию

  Не стоит использовать порядок массива. Перестановка элементов редактором неожиданно изменит поведение карты.

  Лучше:

  - default_start_id на уровне карты; либо
  - default: true у одного старта с проверкой уникальности.

  Я предпочитаю default_start_id: один явный источник истины. Если он отсутствует:

  1. при единственном старте выбрать его;
  2. при нескольких потребовать выбор;
  3. для тестового запуска можно временно выбрать первый, но показать предупреждение.

  ## Что делать с точками героя и компаньонов

  Сейчас карта ожидает отдельную core:hero_start и по одной core:companion_start на каждого жителя. Валидатор напрямую
  связывает количество населения с количеством точек. Это видно [map_validator.gd]home/code-happ/features/world/application/
  map_validator.gd:85).

  Для переменной численности группы это слишком жёстко. область
  ├── orientation
  ├── leader slot
  ├── explicit slots[0..N]
  ├── fallback formation
  ├── allowed actor tags
  └── capacity


  Алгоритм:

  1. Лидер занимает именованный `leader`-слот.
  2. Компаньоны занимают явные слоты по приоритету.
  3. Если персонажей больше — система достраивает формацию внутри spawn-area.
  4. Каждая позиция проверяется по навигации, воде, уклону, коллизиям и профилю перемещения.
  5. Если вместимости недостаточно — запуск блокируется с понятной ошибкой.

  Явные точки всё равно полезны для постановочных сценариев, но не должны быть единственным способом разместить группу.

  Нужны разные семантики:

  - `party_spawn` — группа игрока;
  - `actor_spawn` — конкретный авторский NPC;
  - `reinforcement_spawn` — место будущего сценарного появления;
  - `player_spawn` — слот игрока/команды;
  - `camera_start` — начальный вид;
  - `respawn` — отдельная механика, не равная начальному старту.

  При этом закрытый список ролей можно сохранить (`spawn` остаётся геометрической ролью), а конкретное значение выражать через
  `function` и данные компонента.

  ## Ресурсы и снаряжение

  Здесь нужен не один способ, а три — для разных намерений.

  ### Дефолт игры

  «В обычном Settlement игрок начинает с 500 монетами» — это дефолт game definition или модуля.

  Это уже примерно так работает в [settlement.gdgame.json](/home/ivank/_personal/codeWorkspace/go-to-happyness/game/content/
  core/games/settlement.gdgame.json:1).

  ### Ограничение или вариант карты

  «На этой суровой карте стартовый бюджет ограничен 200 монетами» — override стартового варианта карты.

  Но карта не должна знать общий словарь всех возможных ресурсов движка. Override принадлежит модулю:

  ```json
  "module_settings": {
    "gth.settlement": {
      "starting_money": 200
    }
  }

  ### Физические предметы в мире

  «У северного старта стоит телега с едой и инструментами» — сущность карты с inventory/container-компонентом.

  Это особенно важно для приключений:

  - предмет можно не заметить;
  - его можно украсть;
  - рюкзак может лежать в другом месте;
  - разные персонажи могут иметь разные предметы;
  - контейнер существует физически и сохраняется.

  Таким образом:

  - деньги, репутация, wellbeing — параметры модуля;
  - физические ресурсы и оборудование — inventories сущностей;
  - стартовый личный loadout — профиль состава группы либо inventory конкретного actor;
  - набор, зависящий от выбранного старта, — ссылка loadout_id из StartOption.

  Сейчас в коде уже намечено решение через backpack entity, но документация одновременно говорит, что вся стартовая экономика
  задаётся game definition. Это стоит привести к одному ясному правилу.

  ## Компаньоны

  Нужно разделить количество, состав и размещение.

  - party_size — параметр запуска.
  - party_roster — конкретный состав.
  - party_template — правила генерации состава.
  - spawn_group — только размещение.
  - loadout — предметы и оснащение.

  Точка спавна не должна решать, кто является компаньоном и что у него в карманах. Иначе геометрия карты начинает владеть
  правилами граждан, классов и инвентаря.

  Для карты возможны три режима состава:

  - generated — модуль создаёт N персонажей;
  - fixed — сценарий задаёт конкретных персонажей;
  - player_selected — игрок собирает группу перед запуском.

  В StartOption достаточно ссылки на roster/template, но интерпретирует её соответствующий модуль.

  ## Гравитация и высота прыжка

  Их не стоит ставить рядом как параметры карты: это данные разных уровней.

  ### Гравитация

  Гравитация — свойство мира или физического окружения. Она уже присутствует в BiomeDefinition, что концептуально спорно: биом
  «летний лес» не должен определять физические законы.

  Лучше ввести world physics profile:

  "environment": {
    "physics_profile": "core:earth",
    "gravity": [0, -9.8, 0]
  }

  Но обычный редактор должен показывать только профиль:

  - Земля;
  - Луна;
  - Марс;
  - Невесомость;
  - пользовательский профиль.

  Ручной вектор гравитации — только в расширенном режиме. И обязательно требуется валидация модулей: settlement-навигация,
  вода, частицы и AI могут не поддерживать боковую или нулевую гравитацию.

  Кроме того, нельзя поменять только CharacterBody3D. Гравитацию должны согласованно получать:

  - персонажи;
  - физические тела;
  - снаряды;
  - прыжки;
  - эффекты;
  - расчёт падения;
  - возможно, навигационные профили.

  ### Высота прыжка

  Это свойство не карты, а mobility/actor profile:

  - герой может прыгать на 1,2 м;
  - тяжёлый NPC — на 0,4 м;
  - робот — не прыгает;
  - существо — на 2,5 м.

  Карта может ограничить правило игры вроде «прыжок отключён», но базовая высота должна принадлежать архетипу персонажа или
  модулю управления.

  И лучше хранить именно желаемую высоту и время достижения вершины, а начальную скорость вычислять относительно гравитации:

  jump_velocity = sqrt(2 × |gravity| × jump_height)

  Иначе смена земной гравитации на лунную полностью меняет высоту прыжка.

  Для автора карты важнее не поле «высота прыжка», а валидатор достижимости: способен ли выбранный traveller profile пройти от
  старта к обязательным целям.

  ## Каким должен быть UI

  Текущий единый диалог старта станет тесным. Я бы сделал отдельное рабочее пространство «Старт», а «Сценарий» оставил для
  runtime-правил.

  ### Раздел «Мир»

  - game definition;
  - стиль;
  - календарь и время;
  - погода;
  - physics profile;
  - progression policy;
  - seed policy: случайный, фиксированный, выбираемый игроком.

  ### Раздел «Варианты старта»

  Список слева, карточка справа:

  - ID и локализованное название;
  - доступные game definitions;
  - spawn group;
  - camera anchor;
  - loadout/roster;
  - overrides модулей;
  - доступен ли выбор игроку;
  - условия доступности;
  - кнопка «Сделать стартом по умолчанию»;
  - «Проверить» и «Тестовый запуск отсюда».

  ### Раздел «Параметры игры»

  - значение по умолчанию;
  - override карты;

  - допустимый диапазон;
  - итоговое вычисленное значение.

  Хороший UX показывает происхождение:

  Стартовое население: 6
  Источник: вариант старта «Северный лагерь»
  Дефолт игры: 4
  Игрок может менять: 1…12

  ### Раздел «Начальные сущности»

  Не дублирует редактор наполнения, а показывает связанные объекты:

  - состав группы;
  - контейнеры;
  - транспорт;
  - стартовые здания;
  - недостающие ссылки на контент.

  ### Раздел «Переменные сценария»

  - тип;
  - начальное значение;
  - описание;
  - кто читает/пишет;
  - ссылки на правила;
  - предупреждение о неиспользуемых переменных.

  ## 1. Не «переменные и константы», а четыре категории данных

  Термины «константа» и «переменная» для UI редактора не очень удачны. Автору карты важнее понимать, кто может менять значение
  и когда.

  ### 1. Свойства мира

  Не меняются после создания сессии либо меняются только специальной механикой:

  - размер карты;
  - размер клетки;
  - тип и уровень границы;
  - географическая широта;
  - базовая гравитация;
  - набор обязательного контента;
  - допустимые игровые определения;
  - стиль мира.

  Это не константы движка, а авторские свойства конкретного мира. В сейве они сохраняются как часть идентичности карты.

  Размер карты после авторинга действительно лучше считать неизменяемым. Широта или гравитация технически могут изменяться
  сценарием, но обычный редактор не должен представлять их как постоянно изменяемые игровые переменные.

  ### 2. Начальные значения состояния

  Устанавливаются один раз при старте, после чего становятся обычным состоянием сессии:

  - день года;
  - время суток;
  - текущая погода;
  - деньги;
  - благополучие;
  - стартовая численность;
  - содержимое инвентарей;
  - активная эпоха;
  - стартовые отношения и репутация;
  - начальные значения сценарных флагов.

  Например, time_of_day = 480 — не константа. Это начальное значение часов. После запуска время идёт дальше.

  ### 3. Ограничения сессии

  Они задают не состояние, а разрешённый диапазон:

  - доступные эпохи;
  - минимальная и максимальная численность группы;
  - разрешённые стартовые позиции;
  - разрешённые фракции;
  - доступные сложности;
  - возможность ручного выбора точки старта;
  - допустимые погодные пресеты;
  - разрешённые игровые модули или режимы.

  ### 4. Runtime-переменные сценария

  Меняются правилами уже во время игры:

  - bridge_open;
  - bandits_defeated;
  - reinforcements_arrived;
  - счётчики волн;
  - контроль зон;
  - таймеры;
  - победа/поражение.

  Их не надо смешивать с начальными параметрами карты. В start могут лежать только их начальные значения, а владельцем остаётся
  сценарий.

  Поэтому отдельные панели «Константы» и «Переменные» я бы не делал. Лучше понятные разделы: «Мир», «Начало сессии», «Варианты
  старта», «Ограничения», «Сценарий».

  ## 2. Старт должен стать набором вариантов

  Одна глобальная коллекция hero_start и companion_start плохо масштабируется. Уже сейчас численность населения выбирается
  параметром, а валидатор требует соответствующее количество отдельных companion-точек. Это связывает геометрию карты с
  конкретным числом персонажей.

  Лучше ввести понятие start preset или entry option:

  "starts": [
    {
      "id": "river_camp",
      "name": "Лагерь у реки",
      "default": true,
      "selectable": true,
      "spawn_group": "river_party",
      "camera_anchor": "river_overview",
      "module_overrides": {
        "gth.settlement": {
          "starting_money": 300
        }
      }
    },
    {
      "id": "mountain_pass",
      "name": "Горный перевал",
      "selectable": true,
      "spawn_group": "mountain_party"
    }
  ]

  Это даёт:

  - несколько точек входа для свободной игры;
  - разные старты одного сценария;
  - отдельные позиции команд в мультиплеере;
  - случайный старт;
  - старт, выбираемый сценарием;
  - разные камеры и вступительные тексты;
  - разные локальные наборы предметов.

  ### Как выбирать старт по умолчанию

  Не стоит использовать порядок массива как основной контракт. После сортировки или редактирования смысл незаметно изменится.

  Лучше одно из двух:

  - default_start: "river_camp" на уровне карты — предпочтительный вариант;
  - либо уникальный default: true у одного варианта.

  Я предпочитаю default_start как явную ссылку: её легче валидировать, показывать и сохранять. Если поле отсутствует:

  1. взять единственный доступный старт;
  2. иначе первый доступный — только как fallback с предупреждением валидатора.

  ## 3. Точки появления лучше объединять в spawn group

  Одна точка на каждого спутника удобна только для заранее фиксированной партии. Для свободной игры нужна модель,
  поддерживающая переменную численность.

  Например:

  {
    "id": "river_party",
    "role": "spawn_group",
    "origin": "river_leader",
    "formation": "loose",
    "radius": 4,
    "capacity": 12,
    "fallback": "nearest_valid",
    "slots": [
      { "id": "leader", "anchor": "river_leader", "tags": ["leader"] },
      { "id": "slot_1", "anchor": "river_1" },
      { "id": "slot_2", "anchor": "river_2" }
    ]
  }

  Правило размещения:

  1. лидер занимает слот с тегом leader;
  2. персонажи с подходящими тегами занимают специализированные слоты;
  3. остальные — свободные авторские слоты;
  4. если партия больше числа слотов, система ищет свободные проходимые позиции внутри радиуса;
  5. если вместимость превышена — запуск запрещается валидатором.

  Это сохраняет авторский контроль над красивой постановкой, но не требует расставлять 24 точки для максимальной численности.

  Роли core:hero_start и core:companion_start можно временно поддерживать как старый формат, преобразуя их в одну неявную spawn
  group.

  ## 4. Ресурсы и компаньоны — не свойства координаты

  Точка появления должна отвечать за:

  - позицию;
  - ориентацию;
  - допустимую аудиторию;
  - порядок/приоритет слота;
  - formation;
  - безопасный радиус;
  - камеру и визуальное направление входа.

  Но не за экономические параметры персонажа.

  Иначе один и тот же компаньон или стартовый набор невозможно будет нормально переиспользовать в другой точке.

  ### Стартовые ресурсы

  Их полезно разделить по физическому владельцу.

  - Общие деньги, репутация, технологии — параметры игрового модуля.
  - Предметы в рюкзаке героя — содержимое стартового персонажа/loadout.
  - Предметы в телеге — содержимое размещённой сущности телеги.
  - Ящики на земле — обычные authored entities карты.
  - Ресурсы на общем складе — состояние стартового здания или модульное стартовое действие.

  Текущая идея с starter_backpack и starter_loot верна для физически существующих предметов. Но она не должна заменять общие
  игровые параметры вроде денег или стартовой репутации.

  Я бы ввёл переиспользуемые loadout-определения в паках:

  {
    "id": "core:settler_basic",
    "items": {
      "core:food": 3,
      "core:tool_axe": 1
    }
  }

  А стартовый состав ссылается на них. Карта может выбрать loadout или ограничить список, но не обязана копировать перечень
  предметов.

  ### Компаньоны

  Нужно разделить:

  - архетип персонажа;
  - конкретную authored identity;
  - роль в партии;
  - loadout;
  - позицию появления.

  Пример состава:

  "party": {
    "min_size": 1,
    "max_size": 8,
    "members": [
      {
        "id": "leader",
        "archetype": "core:settler",
        "required": true,
        "tags": ["leader"],
        "loadout": "core:leader_basic"
      }
    ],
    "optional_pool": [
      {
        "archetype": "core:settler",
        "weight": 1,
        "loadout": "core:settler_basic"
      }
    ]
  }

  Для settlement-песочницы численность можно выбирать при запуске. Для сюжетной карты автор может зафиксировать конкретных
  персонажей. Spawn group только распределит выбранный состав по местам.

  ## 5. Где должны жить значения по умолчанию

  Полезен такой порядок наложения:

  дефолт модуля
  → дефолт game definition
  → ограничение/override карты
  → выбранный start preset
  → выбор игрока в меню запуска
  → сценарные изменения после старта

  Именно ограничение и override — разные вещи.

  Например:

  - game definition предлагает население 1…24, default 4;
  - карта поддерживает только 2…8;
  - пресет «Тяжёлый старт» предлагает 2;
  - игрок выбирает 3.

  Для этого нынешнего StartParameterDef мало: он описывает тип, min/max и default, но не различает:

  - скрытый фиксированный параметр;
  - редактируемый игроком;
  - только авторский параметр;
  - ограничение диапазона;
  - map override;
  - зависимость от выбранного старта;
  - ссылки на контент;
  - структурированные словари ресурсов/loadout.

  Нужны дополнительные метаданные вроде:

  - scope: world | module | player | scenario;
  - authoring: hidden | read_only | editable;
  - launch_visibility;
  - override_policy: replace | restrict | merge;
  - required;
  - content_kind;
  - description;
  - advanced;
  - условия видимости.

  Тогда UI редактора остаётся полностью data-driven и не узнаёт, что такое settlement, shooter или colony.

  ## 6. Гравитация и высота прыжка

  Это два параметра разных владельцев.

  ### Гравитация

  Гравитация — свойство мира/физического окружения. Сейчас она находится в BiomeDefinition, но концептуально это спорно: лес и
  пустыня не должны менять физику планеты.

  Лучше иметь world_physics_profile, например:

  "physics": {
    "profile": "core:earth",
    "gravity": [0, -9.8, 0]
  }

  Обычная карта выбирает профиль. Числовой override показывается только в «Расширенных настройках». Для Луны или астероида пак
  добавляет другой профиль.

  Важно: изменение гравитации влияет не только на героя, но также на:

  - падение персонажей и предметов;
  - баллистику;
  - частицы, если они физически согласованы с миром;
  - fall damage;
  - навигационные профили;
  - анимации;
  - расчёт прыжка;
  - плавающие/летающие сущности.

  Поэтому gravity нельзя прятать в настройках одного персонажа или settlement-модуля.

  ### Высота прыжка

  Высота прыжка — характеристика actor/mobility profile, а не карты.

  У карты могут быть:

  - требуемый профиль передвижения;
  - запрет прыжка;
  - глобальный модификатор;
  - зоны с модификаторами;
  - требования доступности стартов и целей.

  Но базовые jump_height, скорость, ускорение, step height и радиус принадлежат архетипу персонажа или traveller profile.

  Также лучше авторить именно желаемую высоту прыжка, а импульс вычислять из гравитации:

  jump_velocity = sqrt(2 × gravity_magnitude × jump_height)

  Иначе после изменения гравитации персонаж начнёт прыгать на неожиданную высоту.

  Для settlement-жителей автоматический «прыжок из препятствия» вообще не должен определять проходимость карты. Навигация
  должна считать допустимый перепад через traveller profile, а прыжок оставаться способом выполнения движения или аварийного
  освобождения.

  ## 7. Каким должен быть UI «Старт карты»

  Я бы отказался от одного небольшого диалога. По мере добавления модулей он станет неудобным. Лучше отдельная рабочая область
  с разделами.

  ### Мир

  - Game definition.
  - Стиль мира.
  - География: день года, широта.
  - Стартовое время и погода.
  - Physics profile.
  - Граница карты.
  - Seed policy: фиксированный, случайный, выбираемый игроком.
  - Обязательные паки и отсутствующие зависимости.

  ### Варианты старта

  Список карточек:

  - id и локализованное имя;
  - доступен ли игроку;
  - старт по умолчанию;
  - spawn group;
  - стартовая камера;
  - вступительный текст;
  - preview/thumbnail;
  - ограничения по игроку, фракции или режиму;
  - module overrides.

  На карте при выборе карточки должны подсвечиваться её spawn group, камера и связанные сущности.

  ### Состав и имущество

  Генерируется выбранными игровыми модулями:

  - размер партии;
  - обязательные персонажи;
  - пул дополнительных персонажей;
  - loadouts;
  - деньги и глобальные ресурсы;
  - стартовые технологии;
  - здания/транспорт, с которыми начинается игра.

  ### Прогрессия и ограничения

  - доступные эпохи;
  - стартовая эпоха;
  - разрешённые технологии;
  - фиксированные и выбираемые параметры;
  - сложность;
  - правила сохранения;
  - условия multiplayer slots/factions.

  ### Диагностика

  До запуска показывать:

  - нет default start;
  - несколько default start;
  - spawn group не существует;
  - недостаточная вместимость;
  - точка в воде или непроходимой клетке;
  - камера смотрит за карту;
  - отсутствует архетип/loadout;
  - game definition не установлена;
  - карта требует модуль, которого нет;
  - старт недостижим до обязательной цели;
  - выбранная партия не помещается;
  - стартовый контейнер имеет недопустимое содержимое.

  Кнопка «Тестовый запуск» должна позволять выбрать конкретный start preset и граничные значения: минимальную и максимальную
  партию.

  ## 8. Что ещё важно учесть для пользовательских паков

  Несколько вещей, которых обычно не хватает в первой версии.

  ### Локализация

  Имена стартов, описания, сообщения и подсказки должны быть локализуемыми ключами паков, а не только строками внутри карты.

  ### Стабильные ID

  Start preset, spawn group, slots, персонажи и loadouts должны иметь стабильные ID. Сценарий и сейвы ссылаются на ID, никогда
  не на индекс массива.

  ### Отсутствующий контент

  Редактор должен различать:

  - обязательную зависимость — карта не запускается;
  - необязательный контент — используется fallback;
  - неизвестное модульное поле — сохраняется без потери, даже если модуль сейчас не установлен.

  Это особенно важно, если пользователь открыл карту без одного из исходных паков.

  ### Версии и миграции

  Не следует повышать формат всей карты при добавлении каждого параметра модуля. Общая оболочка карты версионируется хостом, а
  module_settings желательно иметь с версиями владельцев:

  "module_settings": {
    "gth.settlement": {
      "version": 2,
      "values": {}
    }
  }

  Мигрировать эту секцию должен модуль, который понимает её смысл.

  ### Determinism

  Нужно явно хранить политику seed:

  - фиксированный автором;
  - случайный на каждую сессию;
  - вводимый игроком;
  - производный от start preset.

  И отдельно понимать, что seed не должен менять authored terrain — только разрешённые процедурные выборы: состав пула, погоду,
  события и т. п.

  ### Multiplayer

  Даже если его пока нет, модель стартов не должна его запрещать. Нужны:

  - team/faction slots;
  - эксклюзивные и совместные spawn groups;
  - минимальное/максимальное число игроков;
  - симметричность или предупреждение о дисбалансе;
  - безопасная дистанция между командами;
  - порядок выбора стартов;
  - spectator/camera start.

  ### Возобновление и сейвы

  Start preset применяется один раз. При загрузке сейва нельзя повторно выдавать предметы, создавать персонажей или
  переустанавливать погоду.

  В сейве полезно записывать:

  - ID выбранного старта;
  - разрешённые параметры запуска;
  - фактически созданный состав;
  - revision карты и game definition.

  ## Итоговая рекомендация

  Текущие MapStart, GameDefinition.start.modules, StartParameterDef и anchors не нужно выбрасывать. Их стоит развить в
  следующую модель:

  Map
  ├── world properties
  ├── initial world state
  ├── start presets[]
  │   ├── spawn group
  │   ├── camera
  │   ├── party/loadout selection
  │   └── module overrides
  ├── module constraints
  └── scenario initial state

  Самые важные изменения:

  1. Ввести несколько именованных start preset и явный default_start.
  2. Заменить жёсткую связь «один companion — одна обязательная точка» на spawn group с авторскими слотами, вместимостью и
     fallback-размещением.

  3. Отделить состав/loadout от координат.
  4. Хранить физические предметы в сущностях и контейнерах, а абстрактную экономику — в параметрах игрового модуля.
  5. Перенести гравитацию из понятия биома в physics profile мира.
  6. Оставить высоту прыжка в mobility profile персонажа, вычисляя импульс с учётом гравитации.
  7. Расширить StartParameterDef, чтобы он описывал override, restriction, visibility и ссылки на контент.
  8. Превратить нынешний диалог старта в полноценную data-driven рабочую область.

  Это даст и простую settlement-карту, и сюжетный сценарий, и арену, и будущую multiplayer-карту без появления отдельных
  несовместимых форматов. Текущие границы проекта уже ведут примерно туда, но именно start presets, spawn groups и явное
  разделение владельцев данных сейчас являются главным недостающим звеном.
