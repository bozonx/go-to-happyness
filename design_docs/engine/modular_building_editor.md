# Модульный редактор зданий

## 1. Назначение и границы миграции

Модульный редактор создаёт единый открытый формат `.gdbuilding.json` для
встроенных и пользовательских зданий. Старые здания продолжают использовать
`building_blueprints.gd`; новый resolver выбирает JSON только для уже созданных
модульных определений. Массовая миграция старых зданий выполняется отдельно.

Здание разделяется на три понятия:

- `BuildingBlueprint` — неизменяемое описание содержимого;
- `BuildingRuntimeState` — состояние построенного экземпляра и активных зон;
- `BuildingView` — меши, коллизии и маркеры Godot.

Редактор находится в feature `buildings`:

```text
game/features/buildings/
  domain/editor/       # формат, блоки, материалы, зоны, сетка
  application/         # состояние экземпляра и runtime зон
  presentation/        # файловый resolver и игровые визуальные адаптеры
  presentation/editor/ # сцена редактора, repository и визуальные инструменты
```

Встроенные `.gdbuilding.json` лежат вне фичи, в паке контента
`res://game/content/core/buildings/` (см. [content_packaging.md](content_packaging.md) §5.1).

## 2. Сетка и каркас

Основная строительная сетка имеет ячейку `1 × 1 × 1 м` и целочисленные
координаты `Vector3i`. Она используется для кубов, плит, панелей, проёмов,
углов, крыш, лестниц и ограждений.

Шаг размещения предметов наполнения не фиксируется форматом каркаса. Его правила
описаны в отдельном документе [«Наполнение здания»](building_furnishing.md).

Каждый блок содержит:

```json
{
  "pos": [0, 0, 0],
  "block_id": "column",
  "material_id": "earth",
  "rot": 0,
  "variant": "round_med",
  "anchor": [-1, 1]
}
```

`block_id` определяет геометрию, `material_id` — внешний материал каркаса и
реальный строительный ресурс. Поле `variant` присутствует только у блоков с
заготовленными размерами (§3.1) и выбирает один из них; `anchor` — только когда
блок прижат к стороне ячейки (§3.1). Для обычных центрированных блоков оба поля
опускаются.

`pos` — это адрес опорной ячейки, а **не уникальный ключ блока**. В одной ячейке
допустимо несколько записей каркаса: например, две тонкие колонны с разными
ориентациями или привязками. Допустимость определяется фактическим занимаемым
объёмом каждого блока (§3.1), а не тем, различаются ли их материал или вариант.

Материал не выбирается напрямую из полного каталога. Сначала выбирается **эра
здания** (`category`), и уже она задаёт набор доступных материалов. Материалы
кумулятивны: здание эры может использовать материалы своей эры и всех
предыдущих, поэтому в каждой эре доступно несколько материалов. Материал по
умолчанию — «определяющий» материал самой эры (например `earth` для земляной).

| material_id | Игровой ресурс | Эра появления |
|---|---|---|
| `branches` | `branches` | tent |
| `thatch` | `grass` | tent |
| `tarp` | `tarp` | tent |
| `earth` | `soil` | earth |
| `clay` | `clay` | clay |
| `logs` | `logs` | wood |
| `wood` | `boards` | wood |
| `stone` | `stone` | stone |
| `brick` | `bricks` | brick |

Порядок эр: `tent → earth → clay → wood → stone → brick`. Сохранение
проверяет, что каждый блок использует материал, доступный в выбранной эре;
блок с материалом более поздней эры отклоняется. Список материалов в редакторе
перестраивается при смене эры, а редактор предупреждает, если уже размещённые
блоки не соответствуют новой эре.

Стоимость `construction_cost` вычисляется из блоков при сохранении. Редактор не
создаёт новые идентификаторы ресурсов, отсутствующие в `ResourceIds`.

## 3. Режимы редактора

Редактор имеет четыре независимых этапа.

### 3.1. Каркас

- установка и удаление блоков;
- поворот на четверть оборота;
- выбор уровня Y;
- две кисти: **линия** (протягивание) и **прямоугольник** (заливка целого пола
  или потолка на активном слое Y). Прямоугольная кисть работает и для установки,
  и для стирания;
- материал берётся из выбранной эры (см. §2), а не выбирается для каждого блока
  из полного каталога;
- стиль постройки `surface` / `underground`.

Подземные сооружения (`underground`) доступны только начиная с земляной эры
(`earth`) — раньше нет ни инструментов, ни технологии рытья. В редакторе пункт
«Подземная» заблокирован для палаточной эры, а сохранение отклоняет подземное
здание эры `tent`.

**Категории блоков.** Конструкция, фундамент, стены, колонны, крыша, проходы,
**проёмы** (окно, дверь, арка) и **ограждения** (перила с балясинами, парапет).
Каталог состоит из базовых элементов, а не из готовых составных фигур:
прямоугольник собирается из малых кубов, крестовина — из двух совместимых
тонких колонн. Отдельного «спецблока» больше нет: арка — это проём, а не особый
тип. Позже часто повторяемые композиции могут быть добавлены как пресеты кисти,
но сохраняются они теми же базовыми блоками.

**Заготовленные размеры (варианты).** Размер выбирается дополнительным контролом
после выбора типа блока, из фиксированного набора, а не свободным ползунком: так
сохраняются привязка к сетке, детерминированная стоимость и простая палитра. В
формате этот выбор хранится в техническом поле `variant` (пусто = первый размер
по умолчанию).

Набор каркасных размеров:

- **Конструкции:** куб — `1`, `0.5`, `0.25` м; плита — толщиной `0.5` или
  `0.25` м.
- **Колонны:** квадратная — `0.5` или `0.25` м; круглая — `1`, `0.5` или
  `0.25` м; полуколонна — `1`, `0.5` или `0.25` м.
- Остальные категории и их подготовленные профили остаются без изменения.

**Привязка в ячейке (`anchor`).** Блок тоньше 1 м можно прижать к стороне своей
ячейки, а не центрировать: колонну — в угол или к грани, перила/парапет — к краю.
Привязка — это селектор 3×3 в системе координат ячейки: `Vector2i(ax, az)`, каждая
компонента ∈ {−1, 0, +1} (−1 = к минимальной стороне, 0 = по центру, +1 = к
максимальной). Она задаётся в кадре ячейки и не зависит от поворота блока —
всегда «прижать к этой стороне ячейки»; поворот на 90° меняет, какая ось блока
тонкая, и селектор это учитывает. Полноразмерные по оси блоки привязку по этой оси
игнорируют. В формате поле `anchor` пишется только когда блок смещён (`[ax, az]`).

**Занимаемый объём и наложения.** У каждого сочетания `block_id` + `variant` есть
канонический локальный объём (authoring AABB или эквивалентная простая форма) в
границах ячейки. Поворот и `anchor` преобразуют его в объём на сетке. Перед
установкой, перемещением и сохранением редактор проверяет пересечение этого
объёма с уже размещёнными блоками:

- касание гранью, ребром или точкой разрешено;
- пересечение внутреннего объёма запрещено по умолчанию;
- полный куб, стена или иной полноразмерный элемент поэтому конфликтует с
  любым элементом, который занимает ту же часть пространства;
- несколько тонких элементов могут иметь один `pos`, если их объёмы не
  пересекаются; различие материала, ID или варианта само по себе не даёт права
  на наложение;
- пересечение, необходимое для конструктивного соединения (например две тонкие
  колонны, образующие крестовину), разрешается только при явной совместимой
  политике определения обоих блоков: `overlap_policy: structural_joint`;
  редактор допускает лишь обозначенный соединительный объём, но не два полных
  дубликата друг в друге;
- другие исключения для намеренно пересекающихся декоративных форм также
  задаются явной `overlap_policy`, а не неявным правилом редактора.

Это authoring-проверка геометрии. Коллизия, навигационная блокировка и стоимость
по-прежнему выводятся из итогового набора блоков и задаются отдельными правилами
рендера/игры.

**UI кисти.** Палитра — одна кнопка на блок. Размер/профиль (варианты) и привязка
(панель 3×3) выбираются в контекстном инспекторе кисти под палитрой для выбранного
блока — это держит палитру короткой и не плодит `размеры × привязки` кнопок.

**Фундамент** (`foundation`) — отдельный тип с особым поведением при рендере: если
здание стоит на неровной поверхности, фундаментные блоки автоматически
продолжаются вниз до земли, чтобы под домом не оставалось пустоты. В формате это
обычный блок; «уход под землю» вычисляется презентацией по рельефу, а не хранится
покоординатно.

### 3.2. Отделка

Отделка изменяет поверхности уже установленных блоков: штукатурку, обои,
фасады, плинтусы, карнизы и другие покрытия. Она хранится отдельно в
`surface_finishes` и `decor_trims` и не меняет ресурс каркасного блока.

### 3.3. Наполнение

Режим «Наполнение» размещает визуальные предметы, принадлежащие чертежу
здания. Его формат, UX, свойства, правила сетки и коллизии определены в
отдельном документе [«Наполнение здания»](building_furnishing.md).

Визуальные предметы наполнения не владеют логистикой, AI и экономикой.
Функциональность задают связанные с ними `fixtures`, а принадлежность части
здания и требования к оборудованию — активные зоны.

Целевая модель наполнения разделяет визуальные предметы, функциональные
`fixtures` и их runtime-состояние. Связь fixtures с зонами и требования
capabilities описаны в документах [«Наполнение здания»](building_furnishing.md)
и [«Активные зоны»](active_zones.md).


### 3.4. Активные зоны

Активные зоны — области, точки и маршруты, их роли, права доступа, инварианты,
валидация и HUD режима зон — описаны в отдельном документе
[«Активные зоны»](active_zones.md). Он владеет моделью целиком и общий для этого
редактора и редактора ландшафта.

Здесь остаётся только то, что относится к формату здания: массивы `areas[]`,
`anchors[]`, `routes[]` записываются в `.gdbuilding.json` (§7) в координатах
доски `[0…footprint]` (§7.1).

## 4. Runtime активных зон и AI

Общий контракт рантайма зон — денормализация на границе загрузки, резервация
слотов, стабильные `ai_id`, наложение сохранения на определения из файла —
описан в [«Активных зонах»](active_zones.md) §9. Ниже только то, что специфично
для построенного здания.

- денормализацию выполняет `building_blueprints` при завершении постройки:
  якоря группируются по `owner`, зоны верхнего уровня выносятся отдельным
  списком; результат рантайм принимает как типизированное состояние внутри
  `BuildingRuntimeState`;
- распределением жителей по зонам занимается `BuildingZoneService`; ИИ читает
  мировую позицию слота через `AIWorldFacade`, а движение и действие выполняет
  только `CitizenActuator`;
- здания без зон продолжают использовать прежние service positions и списки
  `building_type`, пока не переведены на модульный формат.

Игровое наполнение зон — профессии, рецепты, специализированные действия
поддонов — приходит из пака (`active_zones.md` §2) и добавляется отдельными
вертикальными срезами: facts → provider → goal → steps → actuator →
reservations → tests.

## 5. Встроенные и пользовательские файлы

Раскладка файлов, паки, стили и ключи рантайма описаны в
[../core/content_packaging.md](content_packaging.md). Здесь — только то,
что касается самого редактора зданий.

Сегодня используются два источника:

```text
builtin: res://game/content/core/buildings/
player:  user://custom_buildings/
```

и они переезжают в `res://game/content/<pack>/buildings/` и
`user://content/local/buildings/` на фазе 6 плана упаковки. Runtime-ключ
встроенного здания равен его ID; пользовательский получает namespace `user:<id>`,
поэтому пользовательский файл не может незаметно переопределить стандартное здание.

Папки внутри источника **свободные**: загрузчик обходит дерево рекурсивно и
классифицирует файл по его полям `role`/`era`/`style`/`kind` (§7), а не по пути.
Автор раскладывает файлы как ему удобно.

Player mode позволяет задать ID, имя, эру, footprint и стандартное fallback
здание. Пользовательские файлы перечисляются отдельной категорией меню
строительства.

Dev mode — это авторский инструмент для **стандартных зданий игры**, а не
отдельная песочница: он пишет в каноническую папку, из которой читает игровой
`BuildingBlueprintLibrary`, поэтому созданное в dev-режиме здание — ровно то, что
попадает в игру как стандартное. Он доступен **только при запуске из Godot**
(`OS.has_feature("editor")`): в экспортированной сборке `res://` — read-only `.pck`,
и сохранение молча не сработало бы. В собранной игре редактор всегда в player-режиме.
Dev mode позднее получит инструменты компиляции меша и NavMesh-preview.

Сохранение Blueprint атомарно: сначала пишется `.tmp`, затем файл заменяется. При
записи проставляется `revision` — штамп сохранения, общий с картами
(content_packaging.md §7). Перед записью проверяются версия, ID, размеры, блоки,
материалы, эра, соответствие материала блока эре здания, допустимость подземного
стиля для эры, выход занимаемых объёмов за `grid_bounds`, недопустимые пересечения
объёмов и ID зон. Повторяющиеся `pos` сами по себе валидны (§3.1). Для
`kind: "scenery"` проверки эры, стоимости, входов и зон не выполняются: у декорации
этих полей нет.

## 6. Ссылка из игрового сейва и fallback

Пользовательский Blueprint не встраивается целиком в обычный сейв. Постройка
сохраняет ссылку:

```json
{
  "blueprint_ref": {
    "source": "player",
    "id": "my_bakery",
    "revision": "7fa2d194",
    "fallback_building_id": "house"
  }
}
```

Рядом сохраняется только изменяемое runtime-состояние зон:

- существующие zone IDs и определения, необходимые для восстановления;
- назначенные `ai_id`;
- локальные якоря и поддоны;
- ссылка рабочего места жителя на стабильную клетку здания.

Алгоритм загрузки:

1. Найти файл по `(source, id)`.
2. Если файл найден, загрузить актуальную геометрию и наложить сохранённое
   runtime-состояние зон.
3. Если файл отсутствует, построить `fallback_building_id`.
4. Наложить сохранённые зоны на fallback, чтобы рабочие назначения и якоря не
   исчезли полностью.
5. Если отсутствует и fallback, пропустить объект с диагностикой.

`revision` диагностирует изменение файла: это штамп сохранения, который пишется
в сам чертёж и сравнивается через `BuildingBlueprint.revision_id()` — то же
правило, что у карт (`../core/content_packaging.md` §7). Расхождение только
предупреждает: строгое закрепление старой геометрии не требуется,
пользовательские здания остаются самостоятельными редактируемыми файлами.

С введением ролей (§7, v4) в ссылку добавляется `role`: он позволяет подобрать
здание той же роли в другом стиле, если исходный файл пропал, и только затем
опускаться до `fallback_building_id`.

## 7. Формат `.gdbuilding.json`, версия 3

```json
{
  "version": 3,
  "id": "earth_workshop",
  "name": "Земляная мастерская",
  "revision": "68a1c4f30f21",
  "construction_style": "surface",
  "category": "earth",
  "fallback_building_id": "earth_house",
  "grid_bounds": {"x": 6, "y": 3, "z": 5},
  "footprint": [6, 5],
  "entrance": [0, -2],
  "worker_entrances": [[0, -2]],
  "blocks": [],
  "surface_finishes": [],
  "decor_trims": [],
  "objects": [],
  "place_zones": [],
  "zone_anchors": [],
  "construction_cost": {"soil": 20}
}
```

`entrance`/`worker_entrances` — проекция дверей-маршрутизации на клетки доски
размещения (координатное пространство footprint, а не авторская 3D-сетка). Пока
навигация не потребляет якоря напрямую, эти поля остаются и задаются автором.

Файлы прошлого поколения с массивом `work_zones` читаются через встроенную
миграцию на загрузке: каждая старая зона разбивается на одну `place_zones`-
запись и её `zone_anchors` (рабочие якоря → слоты, поддоны →
`input_tray`/`output_tray`). Запись всегда выполняется в новом формате.

### 7.1. Две координатные системы и версии формата

Формат совмещает два пространства, и они не смешиваются:

- **Индекс ячейки каркаса** (`blocks[].pos`, §2) — целочисленный, без знака,
  `0…N-1` по каждой оси. Это адрес в массиве, а не размещение;
- **Пивот здания** — центр footprint, точка, вокруг которой игра поворачивает
  и позиционирует построенное здание (см. `BuildingEntrancePositions`).
  `entrance`/`worker_entrances` всегда были заданы относительно него как
  знаковые смещения (`[0, -2]`), и с версии 3 формата туда же переведены
  `objects[].pos` (см. [«Наполнение здания», §3.1](building_furnishing.md)).
  `place_zones`/`zone_anchors` остаются в координатах доски `[0…footprint]` —
  их геометрия ссылается на конкретные ячейки каркаса.

Пивот вычисляется как `footprint * 0.5` и не хранится в файле явно
(`BuildingBlueprint.pivot_offset()`). Внутри редактора все инструменты
по-прежнему работают в координатах доски `(0,0)`…`footprint` — перевод
происходит только при записи/чтении файла, так что drag, snap, границы и
пикинг не завязаны на пивот.

История версий:

- **v1** — исходный формат каркаса и зон (§2–§4, §6);
- **v2** — единый формат `objects[]`/`fixtures[]` для наполнения здания
  (`properties` → `appearance`, `is_lit` → `visual_flame_visible`;
  см. [наполнение здания](building_furnishing.md));
- **v3** — `objects[].pos` переведён из координат доски в координаты
  относительно пивота (см. выше). Отдельной миграции v2 → v3 нет: во всех
  файлах проекта на момент перехода декор стоял в начале координат, для
  которого чтение в обеих системах даёт один и тот же результат.
- **v4** (планируется, [../core/content_packaging.md](content_packaging.md) §3)
  — оси идентичности: `role`, `era`, `style`, `kind`. `category` переименовывается
  в `era`, `role` при миграции берётся из `id`, `style` — `"generic"`,
  `kind` — `"building"`. Ни один существующий файл не требует ручной правки.

Поле `revision` появилось вне версий формата: оно необязательно, а его
отсутствие означает «файл старше штампов» и обрабатывается откатом на хеш
содержимого (§6). Добавление необязательного поля не поднимает версию —
её поднимает только смена смысла существующих данных.

## 8. Производительность

Текущий переходный renderer создаёт модуль на блок и подходит для пилотных
Blueprint. До массовой миграции старых и крупных зданий необходим compiler:

```text
Blueprint
  → удаление внутренних граней
  → batching по материалам
  → объединённые коллизии из итогового объединения объёмов
  → LOD
  → игровой BuildingView
```

Отсутствие compiler не блокирует подготовку формата, зон и пользовательского
каталога, но блокирует массовый перевод сложных зданий.
