# Дизайн-документ: Процедурная генерация карт

> Статус: целевой дизайн. Документ задаёт продуктовые правила, формат рецепта и
> границы будущей реализации. Формат результата остаётся форматом карты из
> [map_editor.md](map_editor.md), земля — моделью из
> [grid_terrain_system.md](grid_terrain_system.md), вода — моделью из
> [water.md](water.md), наполнение — моделью из
> [map_fill_mode.md](map_fill_mode.md).

---

## 1. Назначение

Генератор создаёт за один запуск пригодную для игры стартовую карту, которую автор
может сразу запустить, сохранить в пак и продолжить править обычными инструментами
редактора. Он генерирует не картинку, не бесконечный мир и не отдельный процедурный
runtime, а **обычный `MapDocument`** со всеми его слоями:

- целочисленный рельеф `TerrainGrid`, включая корректные террасы и склоны;
- материал поверхности каждой клетки и её допустимые варианты;
- реестр `WaterBody` и клетки `WaterGrid`;
- природное наполнение: деревья, кустарник, камни, залежи и декор;
- по правилам профиля — животных, их поимённые записи либо спавнеры;
- границу, метаданные, стартовые точки и иные явно объявленные секции;
- `required_content` и `preview.png` при сохранении.

После принятия результата происхождение данных не имеет значения. `WorldSession`,
мешер, навигация, сохранения и игровые модули открывают его ровно как авторскую карту.
В `map.json` нет обязательного seed, графа генератора или команды «достроить мир».

### 1.1. Главный инвариант: генерация заканчивается запеканием

Рецепт и seed принадлежат операции создания, а не игровому миру. Результат операции —
снимок данных. Повторная генерация с тем же рецептом заменяет рабочий документ целиком
после подтверждения; она не пытается угадать, какие клетки автор успел поправить.

Это даёт одну модель карты и одно владение каждым слоем. Ручное удаление дерева,
перекраска грунта или углубление озера не создают «исключения из генератора» и не могут
самопроизвольно исчезнуть при следующем открытии.

## 2. Пользовательский сценарий

В диалоге **«Новая карта → Сгенерировать»** автор выбирает:

1. размер доски и вид границы;
2. профиль генерации;
3. seed — число или текст, с кнопками «случайный» и «копировать»;
4. крупные параметры профиля: вода, рельеф, климат, плотность растительности и
   животных;
5. совместимый game definition, если профиль создаёт игровые стартовые точки.

Редактор показывает краткое резюме ограничений и запускает генерацию с индикатором
этапа и прогресса. Автор может отменить её до принятия результата. Готовая карта
открывается как несохранённый `MapDocument`; доступны:

- **Принять** — оставить результат в редакторе и править вручную;
- **Другой вариант** — изменить seed, сохранив параметры;
- **Назад к параметрам** — изменить рецепт;
- **Сохранить как** — записать обычный `.gdmap` атомарным путём
  `MapDocumentService.save_map_to`.

До нажатия «Принять» предыдущий открытый документ не меняется. Генерация не является
командой общего undo: это создание нового документа. После принятия все последующие
операции снова идут через единственный `MapEditorHistory`.

### 2.1. Быстрый и полный предпросмотр

Изменение параметра сначала строит дешёвую 2D-карту высот, воды, материалов и биомов.
Полная генерация создаёт настоящий документ, прогоняет мешер и показывает 3D-вид.
Быстрый предпросмотр никогда не сохраняется и не считается доказательством корректной
навигации.

## 3. Профиль генерации

Профиль — authored content пака, а не GDScript-класс на каждый биом. Рабочее имя
формата — `*.gdmapgen.json`. Он ссылается на стабильные content id материалов,
архетипов и game definition; сам не содержит Godot-сцены и исполняемого кода.

Минимальная форма:

```json
{
  "format_version": 1,
  "kind": "map_generator",
  "id": "temperate_coast",
  "name": "Умеренное побережье",
  "generator_version": 1,
  "board_presets": [96, 128, 256],
  "border": { "kind": "ocean", "level": -2 },
  "terrain": {
    "base_height": 4,
    "relief": 0.55,
    "continent_scale": 0.008,
    "detail_scale": 0.035,
    "erosion_iterations": 3
  },
  "climate": {
    "latitude": 54.0,
    "temperature": 0.55,
    "moisture": 0.65
  },
  "materials": [
    { "id": "core:sand", "when": { "max_height_from_water": 2 } },
    { "id": "core:grass", "weight": 1.0 },
    { "id": "core:rock", "when": { "min_slope_class": "steep" } }
  ],
  "scatter": [
    { "archetype": "core:spruce", "density": 0.34,
      "min_distance": 1.5, "biomes": ["forest"] }
  ],
  "actors": [
    { "archetype": "core:deer_spawner", "per_cells": 4096,
      "biomes": ["forest", "meadow"] }
  ]
}
```

Точные имена параметров фиксируются вертикальным срезом; принцип фиксирован уже
сейчас: профиль выражает **намерение и диапазоны**, а не хранит массив клеток.

### 3.1. Версии и повторяемость

Пара `(profile content key, generator_version)` определяет алгоритм, seed — один
конкретный результат. Изменение порядка случайных выборок, октав, порогов или
постобработки требует поднять `generator_version`.

Одинаковые версия, профиль, параметры, seed и набор зависимостей обязаны давать
побитово одинаковые бинарные слои и одинаково отсортированные записи JSON на одной
поддерживаемой версии проекта. Результат не обещает совпадать между разными версиями
генератора.

Каждый этап получает собственный поток случайных чисел, выведенный стабильным хешем из
главного seed и id этапа (`terrain`, `water`, `materials`, `flora`, `fauna`, `start`).
Добавление выбора животного поэтому не меняет береговую линию и лес.

### 3.2. Зависимости

До запуска профиль разрешает все материалы и архетипы через `ContentIndex.shared()`.
Неизвестная обязательная ссылка останавливает генерацию с понятной ошибкой; она не
заменяется молча. Необязательная группа может объявить fallback. Реально попавшие в
документ ссылки собираются в `required_content` тем же кодом, что при ручном
сохранении карты.

## 4. Детерминированный конвейер

Этапы работают над одним черновиком, но не пишут рабочий документ редактора. Только
успешный конвейер отдаёт законченный `MapDocument`.

### 4.1. Поля макрорельефа

Генератор вычисляет нормализованные поля континентальности, высоты, гряд, локальной
детали, температуры и влажности. Для них используются несколько независимых
`FastNoiseLite`: низкочастотное поле задаёт массу суши, доменное искажение ломает
идеальные окружности, ridged-поле даёт хребты, деталь — локальную неоднородность.

Поля смешиваются кривыми профиля, после чего высота квантуется в целые шаги
`TerrainGrid`. Квантование происходит до гидрологии: вода и материалы обязаны видеть
ту землю, которая действительно сохранится.

Профиль не может записать дробную вершину или произвольный склон. После изменения
колонок штатные правила каскада и `SlopeAssigner` создают только каталог склонов из
`grid_terrain_system.md` §3. Генератор вправе пакетно вычислить дельту, но результат
обязан пройти те же инварианты, что мазок `TerrainService`.

### 4.2. Формирование рельефа

К исходному полю применяются ограниченные дискретные проходы:

1. сглаживание одиночных игл и ям;
2. террасирование в целочисленных высотах;
3. несколько итераций упрощённой эрозии/осыпания;
4. обеспечение допустимого края для выбранной границы;
5. построение дескрипторов склонов.

Эрозия здесь формирует правдоподобную землю, но не симулирует геологию. Каждый проход
имеет фиксированное число итераций и стабильный порядок обхода. Выход за диапазон высот
отклоняет вариант как ошибочный профиль, а не клампится молча.

### 4.3. Гидрология и вода

По финальным целочисленным высотам строятся направление стока и накопление воды.
Локальные минимумы могут стать озёрами, линии высокого накопления — руслами, а клетки,
соединённые с океанической границей ниже её уровня, обрабатываются теми же правилами,
что `BorderOceanService`.

Затем генератор создаёт обычные `WaterBody` и заполняет `WaterGrid` через одну
транзакцию `WaterService`. Тип, уровень, течение и температура водоёма берутся из
профиля. Глубина не генерируется и не хранится: как во всей системе воды, это разница
между уровнем воды и землёй. Генератор не создаёт pond props или второй список мокрых
клеток.

Реки обязаны иметь непрерывный путь к водоёму/границе либо явно заканчиваться в
замкнутом бассейне. Водоём не может состоять из несвязанных островов под одним id.

### 4.4. Материалы поверхности и биомы

Материал назначается после воды и склонов. Решение использует высоту над уровнем воды,
класс склона, влажность, температуру, расстояние до берега и шумовой вариатор.
Жёсткие ограничения применяются первыми (лава, пляж, голая крутая скала), затем
взвешенный выбор среди допустимых материалов.

Биом — вычисленная маска для последующего наполнения и метаданные `biomes[]`, а не
новый слой истины в runtime. Одна карта и одна клетка могут удовлетворять нескольким
тегам: например, `forest`, `wetland` и `mountain`. Поле биома не сохраняется, если ни
один существующий потребитель формата не требует его; последствия уже запечены в
материалах и объектах.

`variant` материала выбирается детерминированно штатными допустимыми вариантами.
`wear` по умолчанию нулевой, `snow_depth` выводится из профиля только для карты, где
снег является начальным авторским состоянием.

### 4.5. Природное наполнение

Растительность, камни, залежи и декор размещаются после стабилизации земли и воды.
Каждое правило задаёт архетипы с весами, плотность, минимальное расстояние, допустимые
материалы/биомы, диапазон высот и уклонов, отношение к воде и размер кластеров.

Кандидаты создаются детерминированным Poisson-disc/blue-noise-подобным разбросом по
чанкам. Затем для каждого кандидата проверяется настоящая `placement`-политика
архетипа, footprint, занятость клетки, поверхность и вода. Генератор не имеет
облегчённой копии этих правил.

Результат запекается по модели fill mode:

- массовые безымянные объекты — в `objects.bin`, когда этот слой реализован;
- до его реализации допустим малый лимит явных `entities[]`, но не десятки тысяч
  JSON-записей;
- объект с авторскими отличиями или ссылочной идентичностью — в `entities[]`;
- порядок бинарных записей стабилен: чанк, строка, колонка, id архетипа, локальный
  порядковый номер.

Генератор не оставляет в карте правило «лес плотностью 0.4». Конкретное дерево после
генерации можно удалить или передвинуть обычным инструментом.

### 4.6. Животные и спавнеры

Животное — не декор. Профиль размещает его только через архетип класса `actor` либо
через архетип спавнера, который исполняет владеющий gameplay-модуль.

- Уникальное или сценарное животное получает устойчивый id в `entities[]`.
- Возобновляемая популяция создаётся через обычный `spawner`, ссылающийся на
  сгенерированную или существующую `region`-зону.
- Если runtime спавнеров ещё не реализован, этап fauna сообщает об этом и пропускается
  только когда группа объявлена необязательной. Генератор не подменяет механику
  пачкой декоративных моделей.

Зоны подходящей среды строятся из связных компонентов маски биома, но записываются как
обычные зоны карты. Вместимость проверяется по площади, footprint и допустимой
плотности; число существ не может превышать физическую ёмкость зоны.

### 4.7. Старт и игровые ограничения

Если профиль создаёт старт, он ищет связную пригодную площадку штатным `NavGrid` и
`TravelerProfile`, а не расстоянием по прямой. Площадка должна:

- находиться на допустимом материале и уклоне, вне глубокой воды и вырезов;
- иметь место для всех обязательных стартовых якорей и footprint;
- иметь заданный диапазон пути до пресной воды и базовых ресурсов;
- иметь минимальную связанную площадь для раннего строительства;
- не пересекаться с опасными зонами и враждебными акторами профиля.

Game-specific требования приходят через объявленный контракт валидатора выбранного
модуля. Генератор мира не знает про костёр, эру или поселенца по имени. Если подходящей
площадки нет, он повторяет только разрешённые профилем стадии с производным seed до
фиксированного лимита попыток, затем возвращает диагностику, а не плохую карту.

### 4.8. Финализация

Перед выдачей результата конвейер:

1. публикует всю землю и воду в `NavGrid` один раз;
2. запускает общий `MapValidator` и валидаторы модулей;
3. проверяет бюджет наполнения и связность обязательных зон;
4. собирает зависимости и сортирует сериализуемые записи;
5. строит миниатюру тем же production-мешером и освещением предпросмотра.

Ошибка этапа содержит id профиля, seed, имя этапа и человекочитаемую причину. Частичный
документ можно сохранить только отдельной отладочной командой разработчика, не через
обычный UI.

## 5. Как максимально используются возможности Godot 4.7

Godot обслуживает техническую реализацию генератора; это не меняет модель результата.

| Задача | Возможность Godot | Правило применения |
| --- | --- | --- |
| Непрерывные поля | `FastNoiseLite` через API `Noise` | Независимый экземпляр и seed на поле; параметры берутся из профиля |
| Случайный выбор | `RandomNumberGenerator` | Только локальный RNG этапа; глобальные `rand*` запрещены |
| Формирование распределений | `Curve` и `Gradient` | Кривые высоты/влажности и цвета 2D-предпросмотра; gameplay-данные не считываются из пикселей |
| Фоновые вычисления | `WorkerThreadPool` | Чтение неизменяемых входов и запись в раздельные буферы чанков; объединение в стабильном порядке |
| Плотные промежуточные данные | `PackedByteArray`, `PackedInt32Array`, `PackedFloat32Array` | Никаких `Object` на клетку; форма совпадает с существующими сетками |
| Черновые карты полей | `Image` / `ImageTexture` | Быстрый 2D-предпросмотр и диагностика, не источник сохранённых данных |
| 3D-предпросмотр | production chunk mesher, `MultiMesh`, `SubViewport` | То же представление, что увидит карта; `SubViewport` делает `preview.png` |
| Прогресс и отмена | сигналы, `Callable`, отменяемая job-модель | UI не блокирует главный поток и никогда не трогается worker-потоком |
| Измерение | `Time`, встроенный Profiler, Performance monitors | Отдельные метрики по стадиям и пиковая память |

`WorkerThreadPool` не даёт права обращаться к `Node`, `SceneTree`, `RenderingServer` или
редакторскому UI из worker-задачи. Параллельны только чистые вычисления массивов.
Создание ресурсов отображения, публикация в сервисы и принятие документа происходят на
главном потоке.

Параллелизм не должен менять результат: чанк получает собственный производный seed,
не читает незавершённый соседний буфер, а merge всегда идёт по координатам чанков.
Проходы со связностью и стоком могут использовать параллельную подготовку, но их
финальное разрешение выполняется в детерминированном порядке.

### 5.1. Что намеренно не используется

- `NavigationServer3D` не заменяет `NavGrid`: gameplay-маршрутизация уже имеет один
  источник проходимости и профили путешественников.
- Физические raycast'ы не определяют высоту для каждого дерева: поверхность известна
  из `TerrainGrid`; физика нужна только для визуальной/отладочной проверки.
- GPU compute не является первым вариантом. Он усложняет headless-тесты и побитовую
  повторяемость. Его можно добавить только как эквивалентный ускоритель с CPU fallback.
- `Resource` (`.tres`) не становится форматом профиля: authored content проекта живёт
  в паках JSON и разрешается через общий content index.

## 6. Архитектурные границы

Код принадлежит feature `world`:

```text
game/features/world/
  domain/generation/
    map_generation_profile.gd
    generation_request.gd
    generation_result.gd
    generation_seed.gd
    fields/...
  application/generation/
    map_generation_service.gd
    generation_pipeline.gd
    stages/...
  presentation/editor/generation/
    map_generation_dialog.tscn
    map_generation_dialog.gd
    generation_preview.gd
```

`domain/generation` — чистые параметры, seed, поля и детерминированные алгоритмы без
Node и файлов. `application/generation` координирует стадии и существующие сервисы.
`presentation` показывает диалог, прогресс и предпросмотр.

Основные границы:

- `MapGenerationService.generate(request) -> GenerationResult` — единственная
  прикладная точка запуска;
- стадии получают типизированный контекст, а не ссылку на `MapEditor`;
- рельеф и вода коммитятся пакетно через `TerrainService` / `WaterService` либо их
  специальный bulk-import API, сохраняющий те же инварианты;
- заполнение использует общую placement-политику fill mode;
- редактор принимает только законченный `MapDocument`;
- `MapDocumentService` остаётся единственным владельцем чтения и атомарной записи
  `.gdmap`;
- никакой стадии не разрешено обращаться к `SettlementGame`.

Bulk API допускается ради скорости, но не как второй write-owner. Он обязан выполнить
валидацию целого буфера, установить его одной транзакцией и один раз опубликовать
меш/навигацию. Цикл из 65 536 отдельных мазков — не корректная реализация пакетной
генерации.

### 6.1. Префабы и генерация

Профиль может размещать готовые `.gdmap`-префабы (руины, роща, лагерь) через общий
placement merge. Префаб сначала проверяет footprint, высоты, воду и конфликт занятости,
затем все его слои вливаются атомарно. Генератор не копирует правила слияния.

---

## 7. Ограничения качества

Карта считается пригодной не потому, что выглядит естественно, а когда выполнены
измеримые условия профиля:

- нет невалидных склонов, вырезов и ссылок на WaterBody;
- обязательные точки связаны требуемым `TravelerProfile`;
- доли суши, воды и материалов лежат в заданных диапазонах;
- нет одноклеточного шума материалов сверх разрешённого профилем;
- старт удовлетворяет ресурсным и пространственным ограничениям;
- все placement-записи валидны и не имеют запрещённых пересечений;
- зависимости разрешаются, id уникальны, неизвестных обязательных архетипов нет;
- число объектов и время генерации укладываются в бюджет пресета.

Рекомендуемые начальные бюджеты для карты 256×256 на целевом desktop CPU:

| Работа | Бюджет |
| --- | ---: |
| Поля + рельеф + вода + материалы | 2 с |
| Наполнение | 2 с |
| Навигация + валидация | 1 с |
| Меш + полный предпросмотр | 3 с |
| Пиковая дополнительная память | 256 МБ |

Это бюджеты профилирования, не обещание интерфейса. Конкретные пороги фиксируются после
первого вертикального среза на CI-машине. Прогресс измеряет завершённые чанки/проходы,
а не искусственный таймер.

---

## 8. Диагностика и инструменты автора

Отладочный overlay переключает слои: исходный noise, итоговая высота, сток,
накопление, вода, температура, влажность, биомы, материалы, кандидаты scatter,
отклонённые placement и стоимость навигации. По клику показываются значения полей,
выбранное правило и причина отклонения кандидата.

В отчёте генерации сохраняются только на время редакторской сессии:

- профиль, версия и seed;
- длительность каждой стадии;
- статистика клеток, водоёмов, материалов и архетипов;
- число повторных попыток старта;
- предупреждения и причины отбраковки.

Кнопка разработчика может экспортировать отчёт и диагностические PNG в `user://`, но
они не входят в `.gdmap` и не нужны runtime.

## 9. Тесты

### 9.1. Domain

- стабильный вывод каждого поля для фиксированного seed;
- независимость потоков seed между стадиями;
- квантование в диапазон `TerrainGrid` без дробных сохранённых высот;
- связность рек и компонентов водоёмов;
- правила материалов на воде, берегу и крутых склонах;
- стабильный scatter, минимальная дистанция и порядок записей;
- отсутствие результата при невыполнимом стартовом ограничении.

Тесты не сравнивают хрупкие скриншоты шума. Они проверяют хеши массивов для нескольких
золотых seed и содержательные инварианты на широком наборе seed.

### 9.2. Application

- генерация → сохранение → загрузка даёт эквивалентный `MapDocument`;
- одинаковый запрос даёт побитово одинаковые `terrain.bin`, `water.bin`,
  `surface.bin` и `objects.bin`;
- отмена не меняет открытый документ и не оставляет временный пакет;
- неизвестный обязательный content id даёт ошибку до дорогих стадий;
- общий `MapValidator` принимает результат каждого встроенного профиля;
- полная публикация навигации выполняется один раз, а не на каждую клетку;
- последовательный и многопоточный режимы дают одинаковый результат.

### 9.3. Scene и визуальная проверка

Один сквозной тест открывает настоящий `map_editor.tscn`, генерирует маленькую карту,
принимает её, сохраняет, заново открывает и запускает через `GameRuntime`.

Для визуальной калибровки профиль имеет набор именованных seed: берег, горная долина,
река, озёрный край, густой лес и редкая растительность. Capture-набор включает:
3D-обзор, воду, крупный план материалов, наполнение, pedestrian/cart nav overlay и
стартовую площадку. Чистый parse или зелёный обзор без nav overlay не считается
визуальной проверкой.

После изменений горячих путей повторно запускается
`tests/repro/diag_terrain_nav_publish_cost.gd`.

## 10. Вертикальные срезы внедрения

### Срез 1 — земля, вода, материалы

- один встроенный профиль умеренного острова;
- диалог seed и основных параметров;
- `FastNoiseLite`-поля, целочисленный рельеф, океан и озёра;
- назначение материалов;
- полный `MapValidator`, навигация и сохранение обычного `.gdmap`;
- быстрый 2D- и production 3D-предпросмотр.

Критерий: две карты с одним запросом побитово совпадают, открываются редактором и
запускаются через `GameRuntime` без специального пути.

### Срез 2 — растительность и ресурсы

- детерминированный scatter по общим placement-правилам;
- `objects.bin` и его таблица архетипов;
- `MultiMesh`-предпросмотр, зависимости и сохранённые дельты runtime;
- диагностические overlays кандидатов.

Критерий: лес на 256×256 не превращается в тысячи JSON-записей, отдельное дерево можно
удалить в fill mode после генерации.

### Срез 3 — животные, префабы и старт

- зоны среды, actor/spawner-архетипы;
- размещение природных префабов;
- модульные требования к стартовой площадке и ограниченные retry;
- полный набор калибровочных seed и бюджеты CI.

Критерий: сгенерированная settlement-карта стартует с достижимыми базовыми ресурсами,
а showcase-карта генерируется без зависимости от settlement-модуля.

---

## 11. Не входит в систему

- бесконечная карта и догенерация чанков во время игры;
- изменение мира из seed при загрузке сейва;
- runtime-эрозия, симуляция рек или сезонное перераспределение биомов;
- генерация правил сценария, квестов и победных условий без явного шаблона профиля;
- ML/LLM-генерация контента;
- отдельные процедурные деревья или животные, обходящие архетипы;
- хранение карты как noise-текстуры вместо `TerrainGrid`/`WaterGrid`;
- гарантия хорошей карты для любой комбинации ползунков: профиль задаёт допустимые
  диапазоны и вправе отклонить противоречивый запрос.
